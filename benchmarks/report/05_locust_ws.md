# T4-4 실시간 WebSocket 부하 — 결론 요약

> 대상: `WS /streams/{bid}/live`

---

## 한 줄 결론

동시 구독자 한계를 재려 했는데, **구독자 1명당 Redis 연결 1개를 붙잡는 구조** 때문에 앱의 연결 풀이 먼저 터졌다. 원래 재려던 팬아웃·CPU 한계는 이 병목에 가려 보지도 못했고, **중계 구조를 뜯어고친 뒤 다시 측정할 대상**으로 남겼다.

---

## 핵심 결론

### 진짜 병목은 Redis 연결 풀 고갈
`/live`는 구독자마다 `xread(block)`로 Redis 연결 1개를 blocking 상태로 점유한다. 그래서 구독자 500명은 통과했지만 800명에서 `MaxConnectionsError`(연결 초과)가 터졌다. 원래 재려던 중계 지연은 이 규모에서 아직 안 밀렸다(문제가 아니었다).

### "구독자 수 = Redis 연결 수"가 확장을 막는 구조적 결함
`INFO clients`로 확인하니 구독자 500명일 때 `blocked_clients`가 정확히 500 — **구독자당 연결 1개가 1:1로 검증**됐다. 같은 stream을 구독자 수만큼 각자 읽으니, 800명이면 채팅 하나에 Redis read가 800번 일어난다. 풀 크기를 키워도 한계를 뒤로 밀 뿐, blocked 연결 낭비는 그대로다.

### 병목은 Redis 서버가 아니라 앱의 연결 풀
Redis 서버 상한(`maxclients`)은 1만으로 여유였고, 터진 건 **redis-py 클라이언트 쪽 풀 상한**(500~800 사이)이었다. 서버 상한과 클라이언트 풀 상한은 별개의 층이라는 걸 놓치면 범인을 못 찾는다.

### CPU·메모리는 병목이 아니었다 (거기까지 도달 못 함)
800 구독자에서도 CPU idle 62%로 여유. 연결 풀이 먼저 터져서, 팬아웃 CPU 부하가 실제로 걸리기 전에 상당수 구독자가 예외로 죽었다. 그래서 "CPU가 먼저 막힌다"던 애초 가설은 **검증 불가**(앞의 연결 병목이 가림).

### 실험의 진짜 수확 = 실서비스 투입 전 아키텍처 결함 발견
숫자가 이상한 것(800이 500보다 나빠 보임)을 노이즈로 넘기지 않고 파고들어 `MaxConnectionsError`를 찾았다. "확장 한계를 재는" 실험이 "구조상 Redis 풀에서 막힌다"는 명확한 답을 줬다.

### 문서 지식 정정
이전 노트의 "Redis 풀은 기본이 무제한이라 조정 불필요"는 **틀렸다.** redis-py 클라이언트 풀에도 상한이 있고, 그게 이 실험의 병목이었다. (DB 풀만 신경 쓰면 된다는 인식이 오류.)

---

## 해결 방향 (다음 과제)

"구독자당 읽기"를 **"하나가 읽어 여럿에 뿌리기"**로 전환한다. 앱 안에 stream을 상시 읽는 태스크 1개를 두고, 구독자는 앱 메모리의 레지스트리에만 등록해 내부에서 배분하는 구조. 이러면 Redis 연결이 구독자 수와 무관해진다. 리디자인 후 재측정하면 이번에 가렸던 팬아웃·CPU·메모리 한계를 비로소 볼 수 있다.

## 핵심 지표 (참조)

| vus (동시 구독자) | 중계 지연 p95 | CPU idle | 상태 |
|---|---|---|---|
| 100 | 12 ms | 83%+ | 여유 |
| 500 | 31 ms | 50%+ | 통과 (풀 안) |
| 800 | 40 ms | 62% | **MaxConnectionsError (풀 초과)** |
| 2000 | 76 ms | 10%대 | 붕괴 |

- 구독자 500 접속 시 `blocked_clients` = **500** (구독자당 Redis 연결 1개, 1:1 검증)
- Redis 서버 `maxclients` = 10,000 (여유) → 병목은 서버가 아니라 **앱 클라이언트 풀**
- 클라이언트 풀 상한은 500~800 사이에 존재
