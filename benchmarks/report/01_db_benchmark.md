# 저장 방식·인덱스 벤치마크

## 실험 1 — 저장 방식 (A ~ E)

**조건:** 실제 수집한 `chats` 테이블에서 로드한 동일한 데이터셋(76,334행)을 대상으로,
배치/커밋 단위는 1000으로 고정하고 커밋 방식과 SQL 문 구성을 변경해 저장했다.
추가 인덱스는 없음. throughput(처리량)은 총행수 / 벽시계 시간으로 계산함.

| 방식                       | 처리량(rows/s) |  행당 ms |       vs A |
| ------------------------ | ----------: | -----: | ---------: |
| A. 행당 commit             |         839 |  1.192 |       1.0× |
| B. 개별 INSERT + 1회 commit |       2,774 |  0.360 |       3.3× |
| C. multirow INSERT       |      86,946 | 0.0115 |     103.6× |
| D. executemany           |      60,941 | 0.0164 |      72.6× |
| E. COPY                  |     151,439 | 0.0066 | **180.5×** |

### 결과 — 단계별 분해

| 구간        |         배율 | 변경된 요소                           |
| --------- | ---------: | -------------------------------- |
| A → B     |       3.3× | 커밋 1000회 → 1회 (**commit 처리 횟수**) |
| B → C     |      31.3× | INSERT 문 1000개 → multirow 1문장    |
| C → E     |       1.7× | multirow → COPY                  |
| **A → E** | **180.5×** | (위 셋의 곱: 3.3 × 31.3 × 1.7)       |


커밋 한 번 비용: 0.81ms
execute 한 번 비용: 0.35ms




### 검증 1 — `synchronous_commit=off` (fsync 영향 확인)

**조건:** 방법 A~E를 `SET synchronous_commit=off` 상태에서 측정.
세션에 설정이 적용됐는지는 `SHOW synchronous_commit`으로 확인했으며 실제로
`off`가 출력되는 것을 확인했다.

이 설정에서는 commit 시 WAL flush를 기다리지 않게 되지만, commit 자체의 처리,
트랜잭션 종료, SQL 실행 등의 다른 비용은 그대로 남는다.

| 방식                 | sync-on | sync-off |        배율 |
| ------------------ | ------: | -------: | --------: |
| A. 행당 commit       |     839 |      999 | **1.19×** |
| B. 개별 INSERT + 1커밋 |   2,774 |    2,887 |     1.04× |
| C. multirow        |  86,946 |   92,078 |     1.06× |
| D. executemany     |  60,941 |   66,459 |     1.09× |
| E. COPY            | 151,439 |  171,141 |     1.13× |

* A의 commit 횟수가 가장 많은 만큼 가장 영향이 많음.

### 검증 2 — commit 격리 (A2)

**조건:** A와 동일하게 행마다 INSERT를 실행하되, 각 행마다 commit하지 않고
모든 INSERT가 끝난 뒤 마지막에 한 번만 commit했다.

이를 통해 "행마다 commit을 호출하는 것"에서 발생하는 비용을 별도로 확인했다.
하네스에는 `m_A2_per_row_no_commit`을 추가했다.

| 방식                             | 처리량(rows/s) | op p50(ms) | op p95(ms) |
| ------------------------------ | ----------: | ---------: | ---------: |
| A. 행당 execute + 행당 commit      |         868 |       1.15 |       1.27 |
| **A2. 행당 execute + commit 제거** |   **2,907** |   **0.34** |       0.39 |
| B. 개별 INSERT + 1커밋             |       2,878 |  (배치당 349) |          — |

commit을 제거하자 건당 지연 시간이 **1.15ms → 0.34ms**로 감소했다.
약 0.81ms/건이 줄어든 것으로, 원래 A의 건당 처리 시간에서 약 70%에 해당한다.

처리량 역시 868 → 2,907 rows/s로 증가해, **A2가 B(2,878 rows/s)와 거의 같은
수준**이 됐다.

즉, execute 자체에 필요한 시간은 약 0.34ms였고, A에서 추가로 발생하던 약 0.81ms는
행마다 commit을 수행하면서 발생한 비용으로 볼 수 있다.

### 종합 결론

| 실험               | 제거한 요소    | A 결과                 | 의미                      |
| ---------------- | --------- | -------------------- | ----------------------- |
| 원본 (sync-on)     | —         | 839, 1.19ms          | 기준선                     |
| 검증 1 (sync-off)  | fsync 대기  | 999, 1.01ms (1.19×)  | fsync는 주요 병목이 아님        |
| 검증 2 (commit 제거) | commit 처리 | 2,907, 0.34ms (3.4×) | **commit 처리 전체가 주요 병목** |

## 실험 2 — 인덱스 구성

**조건:** 저장 방식은 **executemany(D)로 고정**하고(코드 `experiment_indexes` 확인), 인덱스 구성만 변경했다.

비교 기준은 이 실험에서 측정한 `pk_only`(64,365 rows/s)다. 인덱스의 쓰기 비용을
확인하기 위해 비교적 빠른 저장 방식을 사용함.

> 참고: 사용자 파생표의 `D대비_%`는 실험 1의 D(60,941)와 비교한 값이다. 이는 서로
> 다른 실행에서 나온 값이므로, `pk_only`가 실험 1의 D보다 5.6% 빠르다는 사실에는
> 특별한 의미가 없다.

| 구성            | 처리량(rows/s) |  pk 대비 저하 | p50 ms |    p95 ms |
| ------------- | ----------: | --------: | -----: | --------: |
| 1. pk만        |      64,365 |      0.0% |  15.84 |     22.81 |
| 2. 단조 증가 인덱스  |      61,530 |      4.4% |  15.33 |     20.01 |
| 3. 랜덤 인덱스     |      58,684 |      8.8% |  19.42 | **30.00** |
| 4. 인덱스 3개     |      50,507 | **21.5%** |  18.45 |     27.75 |
| 5. unique 인덱스 |      56,284 |     12.6% |  17.49 |     25.02 |

### 해석

* **단조 증가 인덱스의 추가 비용은 4.4%로 비교적 작았다.** 값이 계속 증가하므로
  B-tree의 오른쪽 끝을 중심으로 삽입이 이루어져 페이지 분할이 적고 캐시 지역성도
  상대적으로 좋기 때문이다.

* **랜덤 인덱스는 8.8%의 성능 저하를 보였다.** 삽입 위치가 인덱스 전체에 분산되면서
  페이지 분할과 캐시 미스가 증가하기 때문이다. 특히 p95가 30ms까지 증가해
  중앙값보다 꼬리 지연에 더 큰 영향을 주는 것으로 나타났다.

* **unique 인덱스는 12.6%의 성능 저하를 보였다.** 일반 인덱스 갱신 외에도 삽입 시
  중복 여부를 확인해야 하기 때문에 랜덤 인덱스보다 비용이 높았다.

* **인덱스 3개를 추가했을 때 성능 저하가 21.5%로 가장 컸다.** 하나의 행을 삽입할
  때마다 세 개의 B-tree를 함께 갱신해야 하므로 인덱스 갱신 비용이 누적된다.


### 중요 사항 — 현재 수치를 그대로 일반화하지 않기

이번 21.5%라는 수치는 **현재 데이터 규모와 batch_size=1000이라는 조건에서 측정된
결과**다.

테이블이 커지면 B-tree의 깊이가 증가하고, 인덱스가 메모리에 모두 들어가지 않는
상황에서는 특히 랜덤 인덱스의 접근 비용이 커질 수 있다. 따라서 현재 결과를
"인덱스가 최대 21.5%의 성능만 저하시킨다"라고 일반화해서는 안 된다.

현재 수치는 **인덱스 구성에 따라 쓰기 비용이 증가한다는 방향을 확인한 기준선**으로
보고, 실제 운영 규모에 가까운 데이터로 추가 검증해야 한다.
