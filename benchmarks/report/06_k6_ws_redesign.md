# T4-4 리디자인 검증 — 결론 요약

> 대상: `WS /streams/{bid}/live` (실시간 채팅 중계) — 구조 리디자인 후 재측정

## 무엇을 바꿨나 (리디자인)

기존 "구독자당 xread" 구조를 **"lifespan의 상시 리더 1개 + 구독자 레지스트리 + 앱 내부 배분"** 구조로 변경했다.

- **상시 리더 태스크 1개** — `lifespan`에서 `asyncio.create_task`로 띄워 요청과 무관하게 앱 수명 동안 stream을 tail. Redis 연결은 이 리더의 1개뿐(구독자 수 무관), 앱 종료 시 `task.cancel()`로 정리.
- **구독자 레지스트리** — 앱 메모리의 파이썬 딕셔너리(`dict[bid, set[WebSocket]]`)로 구독자 관리(Redis 아님).
- **`/live` 핸들러는 등록만** — 접속 시 레지스트리에 add, 대기, 끊기면 remove. Redis를 직접 읽지 않음.
- **리더가 배분** — 채팅을 읽으면 해당 bid 구독자 전원에게 앱 내부에서 send.

## 결론

**리디자인 성공.** `/live`의 "구독자당 Redis 연결" 병목이 사라졌다. `blocked_clients`가 구독자 수(500+)에 비례하던 구조에서 워커 수(8)로 고정되는 구조로 바뀌어, 구독자와 Redis 연결이 완전히 분리됐다. 저번에 붕괴하던 800명이 이번엔 여유 구간이 됐고, 같은 stream을 구독자 수만큼 중복으로 읽던 낭비도 리더 1회 읽기로 제거됐다.

**서버 여력은 충분.** 2000명에서 워커 CPU 합이 ~110%(10코어 중 1코어 남짓), 800명 기준 중계 지연 p95는 12ms. 실제 팬아웃 한계는 2000명보다 훨씬 위에 있다.

**단, 순수 서버 한계는 이 장비로 측정 불가.** k6(측정 도구)가 같은 머신에서 CPU 400%를 태워 서버(~110%)보다 먼저 병목이 됐다. 두 프로세스를 나란히 프로파일링해 "측정 도구가 먼저 포화된다"는 것을 CPU 숫자로 증명했다. 따라서 부하 생성기를 별도 머신으로 분리해야 한다.

**측정의 성과.** "동시 구독자 한계"를 재려던 실험이, "병목은 이미 사라졌고 이제는 측정 도구 자체가 병목"이라는 답을 줬다. 한계를 못 잰 게 아니라 왜 이 환경에서 못 재는지를 CPU 프로파일로 규명한 것이 핵심 수확이다.

## 방어 가능한 대표 숫자

- **성능:** 800명 동시 구독 시 중계 지연 p95 12ms (서버·k6 양쪽 건강한 점).
- **여력·한계:** 2000명에서 서버 워커 CPU 합 ~110%로 여유. 병목은 측정 도구(k6 400%)였으며, 순수 서버 한계 측정에는 부하 생성기 분리가 필요함을 CPU 프로파일로 규명.
