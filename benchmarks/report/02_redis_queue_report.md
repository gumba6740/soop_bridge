# Redis Streams 큐 삽입 (수집·처리 분리)

> `roadmap.md` 3–4주차 / `design.md` 2단계의 산출물.
> 목표 문장(`design 7-2`): **"워커를 멈춰도 수집기는 안 밀렸다."** → 달성, 정량 검증 완료.
> 형식은 `roadmap.md` 3장(조건/결과/해석/다음)을 따른다.

---

## 0. 한 줄 요약

직결 파이프라인(수집기가 받아서 바로 DB 저장) 사이에 Redis Streams 큐를 끼워
**수집과 처리를 분리**했다. 워커를 완전히 종료해도 수집기는 무손실로 계속 수신했고, 
워커 재기동 시 밀린 분이 전량 저장되어(DB +97, 유실 0) **"큐가 수신을
저장 지연으로부터 보호한다"를 숫자로 증명**했다.

---

## 1. 무엇을 바꿨나 — 구조 변경

**이전 (직결):**
```
[SOOP 웹소켓] → 수집기: 받기 → DB 저장 → 받기 → ...
                        (받기와 저장이 한 프로세스, 순차)
```

**이후 (큐):**
```
[SOOP 웹소켓] → 수집기(collector): 받기 → Redis XADD → 받기 → ...
                                          │
                                     Redis Streams (완충)
                                          │
                    워커(worker): XREADGROUP → DB 저장 → XACK
```

핵심은 **"받기(수집기)"와 "저장(워커)"을 서로 다른 프로세스로 분리**하고 그 사이에
Redis Streams를 완충지대로 둔 것. 저장이 느려지거나 멈춰도 수신이 막히지 않는다.

### 왜 List가 아니라 Streams인가
- **List**(`LPUSH`/`RPOP`): 꺼내는 순간 사라짐 → 워커가 저장 전 죽으면 그 항목 증발.
  여러 워커 분배·완료 추적 없음.
- **Streams**(`XADD`/`XREADGROUP`/`XACK`): 꺼내도 ACK 전까지 남음(pending) → 워커가
  죽어도 회수(XCLAIM) 가능. consumer group이 여러 워커에 중복 없이 분배.
  이게 동시성·장애대응의 핵심 장치.

## 2. 인프라 — Redis 컨테이너 추가

`docker-compose.yml`에 Redis 서비스 추가. 주요 결정:

- **`--appendonly yes` (AOF)**: Redis는 기본이 인메모리라 재시작 시 큐가 증발한다.
  "죽어도 안 사라지는 완충지대"로 쓰려면 디스크 기록(AOF)이 필수. 단 AOF는 메모리
  대신 디스크가 아니라 **메모리 본체 + 디스크 백업 기록** 구조.
- **볼륨 `redis_data:/data`**: 컨테이너를 지워도 AOF 파일이 남도록 명명 볼륨에 연결.
  (`appendonly`로 `/data`에 기록 + 볼륨으로 컨테이너 밖 보존 = 2겹 내구성)
- **healthcheck `redis-cli ping`**: 준비 완료 확인.

### AOF의 내구성 트레이드오프
`appendfsync` 설정으로 "얼마나 자주 디스크에 확정(fsync)"하는지 조절:

| 설정 | fsync 빈도 | 속도 | 죽을 때 유실 |
|---|---|---|---|
| always | 명령마다 | 느림 | 0 |
| **everysec (기본, 채택)** | 1초마다 (백그라운드) | 빠름 | 최대 1초치 |
| no | OS 위임 | 최속 | 최대 수십 초 |

Postgres의 `synchronous_commit`과 **정확히 같은 트레이드오프**. 1–2주차 벤치에서 만난 fsync 저울을 Redis에서 다시 만남.

## 3. AOF 비용 측정 — "안정성은 공짜에 가까운가"

Redis를 끼우면 AOF 기록이라는 비용이 추가된다. 그 비용을 격리 측정.
**조건:** 동일한 xadd를 AOF on/off로 각각 1만 회, 순수 xadd 지연 측정.

| | 처리량(xadd/s) | p50 | p95 |
|---|---:|---:|---:|
| AOF on (everysec) | 2,564 | 0.377ms | 0.472ms |
| AOF off | 2,414 | 0.394ms | 0.495ms |

**해석:**
- **AOF everysec은 xadd에 유의미한 비용을 안 얹는다.** 두 값 차이(~6%)는 측정 노이즈.
  everysec이 fsync를 1초에 한 번 백그라운드로 미루므로 개별 xadd는 디스크를 안 기다림.
- **단, "AOF는 공짜"가 아니라 "위험(1초 유실)을 지불하고 fsync를 미룬 것".**
  `always`로 바꾸면 매 명령 fsync를 기다려 Postgres A방식처럼 느려진다.

**부수 발견 — xadd도 왕복이 병목:**
처리량 2,564/s는 Redis의 실력이 아니라 **하나씩 `await`로 왕복 대기**한 결과.
Postgres 벤치의 B방식(개별 INSERT, 2,774/s)과 판박이. 파이프라인으로 왕복을 줄이면
수만~수십만까지 오른다(= Postgres B→C multirow와 같은 원리).
→ **다만 실시간 수집은 채팅이 하나씩 오므로 하나씩 xadd가 적합.** 파이프라인은
부하 생성(리플레이)용으로 유보.

## 4. 워커 구현 — XREADGROUP → 저장 → XACK

큐에서 꺼내 DB에 저장하는 소비자. 핵심 3동작:

```
1. XREADGROUP  (">"= 그룹이 아직 안 가져간 새 항목, block=5초 대기)
2. DB INSERT + commit
3. XACK        (저장 성공 후에!)
```

### 지킨 규칙과 이유
- **저장 → ACK 순서 (반대 금지).** ACK부터 하면 저장 전 죽을 때 항목이 pending에서
  빠져 증발. 저장 성공 후 ACK해야 죽어도 pending에 남아 회수 가능.
- **`">"`로 재시작 안전.** 그룹의 `last-delivered-id`를 Redis가 기억 → 워커 재기동 시
  처음부터가 아니라 이어서 처리(중복 방지).
- **XREADGROUP은 pull(워커가 가지러 감).** 워커가 저장하느라 바쁘면 안 가져오므로
  자기 속도 유지. 밀리면 큐에 쌓일 뿐(터지지 않음). ← 무손실의 코드 레벨 이유.

### 겪은 버그 2개
1. **KeyError: 'stream_id'** — `decode_responses` 없으면 필드 키가 바이트(`b"..."`)로
   와서 문자열 키 조회 실패. → 워커 클라이언트에 `decode_responses=True`.
2. **TimeoutError (큐 한산할 때)** — `block=5000`(5초 대기)이 클라이언트 소켓
   타임아웃(더 짧음)과 충돌, 소켓이 먼저 터짐. → `socket_timeout=None`으로 대기
   통제권을 block에 일원화. + `try/except RedisError`로 일시 오류에 재시도(죽지 않게).

## 5. 무손실 검증 — 워커를 죽여도 수집기는 안 밀린다

**큐의 완충 효과 — 정량 확인**

**조건:** 수집기 켠 채 워커만 종료 → 큐 밀림(lag) 관찰 → 워커 재기동. maxlen=100000.

**결과:**

| 시점 | lag | DB count |
|---|---:|---:|
| 워커 종료 중 (수집기만) | 93 | 82,176 |
| 워커 재기동 후 | 0 | 82,273 |

- 워커 종료 중 **lag 0→93** 증가 = 처리 안 된 채팅이 큐에 쌓임.
- **그동안 수집기는 계속 수신(무중단).** — 직결이면 저장이 멈추며 수신도 멈췄을 것.
- 워커 재기동 후 **lag 93→0**, DB **+97건** = 밀린 분이 전량 저장됨. **유실 0.**

**해석:**
- 직결 구조는 저장 지연이 수신을 막아 웹소켓 버퍼가 넘쳐 유실. 큐 구조는 수신과
  저장이 분리되어 **저장이 완전히 멈춰도(워커 0개) 수신 무손실.**
- **밀림은 유실이 아니라 지연.** 워커 재기동 시 큐가 붙잡고 있던 분이 전량 처리됨.


### 지표 읽는 법 (XINFO GROUPS)
- **lag**: 아직 안 읽은 수 = 밀림. (XLEN 아님 — XLEN은 ACK해도 안 줄어 계속 증가)
- **entries-read**: 그룹이 누적 읽은 수.
- **pending**: 읽었지만 ACK 안 된 것 (미완료). 실험 내내 1 = 워커 사망 시 남은 미완료분.
- **last-delivered-id**: 소비 커서. **consumers**: 워커 수(현재 1).

## 6. 왜 큐인가 — 정리된 논거

큐를 쓰는 이유:

1. **받기와 저장의 시간 분리.** 저장의 느림/폭주가 수신을 막지 않게. 폭주 순간에
   저장 완료를 강요당하지 않음(나중에 처리).
2. **받기 자체가 가벼워짐.** xadd는 DB INSERT(트랜잭션·인덱스·fsync)보다
   훨씬 가벼워 수신을 덜 막음.
3. **워커 수평 확장.** 저장이 병목이면 워커만 늘림(consumer group이 중복 없이 분배).
   수집기는 하나여야 함(웹소켓은 접속자 모두에게 같은 채팅을 보내므로 수집기를
   늘리면 중복). **못 늘리는 건 받는 쪽, 늘릴 수 있는 건 저장 쪽.**
4. **죽어도 회수.** pending + XCLAIM으로 워커 사망 시 미처리분 회수.
5. **배치의 딜레마 해소.** 직결 배치는 "빠르지만 모으는 중 죽으면 통째 유실 + 지연".
   큐는 수집기는 하나씩(안전), 워커는 배치(빠름), 모으는 중 죽어도 큐가 안전.

**단, 큐도 만능 아님:** 워커가 평균적으로 유입을 못 따라가면 큐도 무한정 쌓여 터짐.
큐가 막는 건 **일시적 폭주**. 지속 과부하는 워커 증설로 해결.

**규모 정직성:** 이 방송 규모(초당 수십)에선 직결로도 충분. 큐는 "지금 필수라서"가
아니라 **동시성·큐·워커 확장 구조를 연습하려고** 도입 (design 학습 목표).

## 부록 A — "소켓→redis가 소켓→db보다 나은 강점" 재정리

> 계속 물고 늘어진 질문: "어차피 둘 다 어딘가에 저장하는 건데, 저장 동작 하나만 놓고
> 비교하면 redis가 db보다 나은 게 뭔가? 속도인가?" — 이에 대한 정리.

### 속도는 이유가 아니다
파이프라인을 제대로 쓰면 redis(파이프라인)와 db(multirow/COPY)는 처리량이 비슷한 급.
"redis가 빨라서"는 틀린 전제. 그런데도 소켓→redis가 나은 이유가 있다.

### 강점 1 — 저장 동작이 안 "튄다" (속도가 아니라 안정성)
저장의 **무게**가 다르다.
- **소켓→db (INSERT):** 트랜잭션·제약검사·인덱스갱신·WAL·commit(fsync 대기)를 거침.
  하나하나가 **느려질 수 있는 지점**. 인덱스 많으면 느려지고, 디스크 바쁘면 fsync
  밀리고, 체크포인트 돌면 튄다. → **평균은 빨라도 가끔 튄다.**
- **소켓→redis (XADD):** 메모리 끝에 붙이기 하나. 트랜잭션·인덱스·동기 fsync 없음.
  → **거의 항상 일정하게 빠르고, 실패할 구석이 적다. 안 튄다.**

왜 이게 결정적인가: 소켓 수신은 **못 기다려주는 실시간**. 저장이 어쩌다 300ms만 튀어도
그 사이 웹소켓 버퍼(기본 32개)가 넘쳐 유실. redis 저장은 그 "어쩌다 튐"이 거의 없어
소켓을 안 막는다. → **강점은 "평균 속도"가 아니라 "최악의 순간에도 안 느려질 확률".**
평균은 db도 빠를 수 있지만 **db는 가끔 튀고 redis는 안 튄다.**

### 강점 2 — redis가 큰 완충
뒤(워커→db)가 밀려도 안 잃음. 웹소켓 수신 버퍼는 유한(기본 32개)하지만 redis 큐는
10만+(디스크까지). 직결이면 저장이 막힐 때 작은 버퍼가 넘쳐 유실, 큐면 큰 완충이
붙잡음.

### 강점 3 — 뒤쪽을 소켓과 독립적으로 재구성 (궁극적 이유)
소켓→db 직결은 저장이 곧 수신이라, 저장 방식 변경(배치)·저장 증설(워커 다중화)·
저장 실패 재처리를 **전부 소켓 수신을 건드리며** 해야 한다. redis로 한 번 끊으면
뒤쪽(워커→db)은 소켓이 뭘 하든 **독립적으로** 배치 넣고, 여러 개로 늘리고, 죽으면
재처리한다. → "저장이 빠르냐"가 아니라 **"저장을 자유롭게 주무를 수 있느냐"**의 문제.
