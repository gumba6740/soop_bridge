# T4-3 캐싱 효과 — 결론 요약

> 대상: `GET /streams/{bid}/stats` (Redis 집계 조회)에 15초 캐싱 도입.

---

## 한 줄 결론

`/stats`에 캐싱을 켜도 **응답시간은 사실상 변하지 않았지만**, Redis 원본 집계 호출이 340배 줄었다. 캐싱의 이득은 **지연 단축이 아니라 백엔드 부하 경감**으로 나타났다.

---

## 핵심 결론

### 응답시간은 안 줄었다
캐싱 대상인 Redis 집계가 이미 **마이크로초 단위**라 응답시간의 0.02%도 안 된다. 나머지 대부분은 FastAPI 라우팅·의존성 주입·Pydantic 직렬화·소켓·도커 네트워크 왕복 같은 **파이프라인 고정비**라, 인메모리 조회를 없애도 이 고정비는 그대로 남는다.

### 이득은 부하 축에서 나타났다
같은 키를 15초 TTL로 두들기니 히트율 99.9%. Redis 원본 집계 호출이 급감하고, 요청당 명령 수도 2에서 1로 줄었으며 각 명령이 더 가벼워졌다("정렬+다중키" → "단일키 get").

### 지표를 바꿔 봐야 한다 (핵심 교훈)
"응답이 안 빨라졌으니 캐싱이 무의미"가 아니라, **무엇이 개선됐는지 지표를 바꿔 봐야 한다.** 지연 축은 평평하지만 부하 축은 급감했다. 이 부하 경감은 지금 규모에선 체감되지 않지만, 초당 수십만 요청 규모에선 싱글스레드 Redis의 처리량 천장을 올려준다.

### 캐싱은 자동으로 좋은 게 아니다
대가(정확성·복잡성)가 있어, 네 조건을 통과할 때만 값어치가 있다: ① 대상이 매번 하기에 비싼가 ② 부하 경감이 필요한 규모인가 ③ 낡은 값을 허용할 수 있는가 ④ TTL 창당 요청 빈도가 충분한가(명령 수 기준 손익분기는 **창당 요청 4개 이상**). `/stats`는 ①에서 이미 "아니오"에 가까웠고(이미 인메모리), 그래서 지연 이득이 없었다.

## 핵심 지표 (참조)

| 지표 | off (캐싱 없음) | on (캐싱) | 변화 |
|---|---|---|---|
| Redis 원본 집계 호출 | 45,200회 | 133회 | **약 340배 감소 (히트율 99.9%)** |
| 요청당 Redis 명령 | 2.00 | ≈ 1.00 | 절반 + 종류도 경감 |
| p95 응답시간 | 41 ms | 35 ms | 사실상 불변 (오차 범위) |
| p50 응답시간 | 13 ms | 12 ms | 사실상 불변 |
| 실패 | 0 | 0 | — |
