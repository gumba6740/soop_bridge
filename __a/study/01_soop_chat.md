# SOOP 채팅 수집기 — 개발 정리

문서 없는 SOOP 채팅 프로토콜을 개발자도구로 직접 역추적해서, 실시간 채팅을 받아오는 파이썬 수집기를 완성한 기록.

---

## 1. 전체 흐름 (한눈에)

```
① API 호출 (httpx)          →  방송 정보 받기 (CHDOMAIN, FTK, CHATNO 등)
② 그 정보로 wss 주소 조립     →  wss://{CHDOMAIN}:{CHPT+1}/Websocket/{bid}
③ 웹소켓 접속 (websockets)   →  subprotocols=["chat"]
④ CONNECT 패킷 전송          →  "나 입장할게"
⑤ (1초 대기) JOIN 패킷 전송  →  "이 방 채팅 받을게"
⑥ 서버가 채팅을 흘려보냄      →  0005 = 채팅, 0007 = 방송종료
⑦ 핑을 60초마다 전송         →  연결 유지
```

핵심 두 계층:
- **HTTP (1단계)**: 요청 한 번 → 응답 한 번. 방송 정보를 받는 안내데스크.
- **웹소켓 (2단계)**: 연결을 튼 뒤 메시지를 계속 주고받는 전화 통화. 채팅이 여기로 흐름.

---

## 2. 왜 이렇게 하는가 (핵심 원리)

### API가 웹소켓을 "연결해주는" 게 아니다
`player_live_api.php`는 고정 주소지만, 웹소켓을 대신 열어주지 않는다.
"너는 이 채팅 서버(CHDOMAIN)로 접속해라"고 **주소만 알려주는** 안내데스크다.
실제 연결은 내 코드가 직접 연다.

### CHDOMAIN이 매번 바뀌는 이유
SOOP은 채팅 서버가 여러 대(`chat-6E0A4C60`~`6F` 같은 이웃 서버 묶음)라,
호출할 때마다 여유 있는 서버 하나를 **새로 배정**한다.
그래서 접속 직전에 **항상 API를 새로 호출**해서 받은 CHDOMAIN을 그대로 써야 한다.
(개발자도구에 뜬 주소랑 내 값이 끝자리가 달라도 정상 — 서로 다른 두 번의 배정이라 그럼)

### 포트는 +1
API가 주는 `CHPT`(예: 8040)에 **+1** 한 포트(8041)가 실제 웹소켓 포트다.

## 3. 내가 헷갈렸던 것들

### httpx vs requests
- 프로젝트가 async(웹소켓)라 **httpx**로 통일. requests는 동기 전용이라 async 안에서 쓰면 전체가 멈춤.

### data= vs json=
- 서버가 기대하는 body 형식으로 보내야 함.
- 요청 헤더 `Content-Type: application/x-www-form-urlencoded` → **`data=`** (form 형식)
- `application/json`이면 → `json=`
- SOOP API는 form이라 `data=`.

### 요청 헤더는 사실 거의 다 필요 없었다
- cURL엔 헤더가 20개씩 붙지만, 실제 필수는 거의 없음.
- SOOP 채팅 수신은 **헤더/쿠키/파라미터 없이 bid만** 있으면 됨.
- 쿠키(AuthTicket 등)는 로그인/채팅 전송에만 필요. 읽기만 할 거면 불필요.

### 응답 Content-Type이 text/html인데 내용은 JSON
- 서버가 라벨을 부정확하게 붙임. `resp.json()`은 라벨 무시하고 파싱하니 문제없음.

### 길이 필드는 10진수 (`:06d`), 16진수 아님!
- 패킷 헤더의 길이 숫자는 **10진수**로 씀.
- CONNECT는 길이가 짧아(6) 10진수/16진수가 같아서 헷갈렸지만,
  JOIN은 길이가 커서(374) 반드시 `:06d`(10진수)여야 함. `:06x`(16진수)면 서버가 거부.

### 글자 수 ≠ 바이트 수 (그래서 encode 후 길이를 잰다)
- 한글은 UTF-8로 1글자 = 3바이트. `len(문자열)`(글자 수)과 `len(바이트)`(바이트 수)가 다름.
- 서버는 **바이트 수**를 원하므로, `body.encode()` 후 `len()`을 재야 정확함.

### `\x0c`는 4글자가 아니라 1문자
- 소스코드엔 `\x0c`라고 4글자로 적지만, 파이썬은 이걸 **문자 하나**로 해석 (`\n`처럼).
- `len("\x0c")` == 1. b스트링이든 아니든 하나로 침.

### encode를 하는 이유
- 문자열 → 바이트 변환. 이유 둘: ① 바이트 길이를 정확히 재려고 ② 웹소켓은 바이트로 보내야 하니까.
- 예전 `bytes.fromhex()`가 이미 바이트를 만들어줘서 그땐 encode가 안 보였던 것.

### ws.send는 문자열도 받지만
- 문자열 주면 자동 UTF-8 인코딩 + 텍스트 프레임. 바이트 주면 바이너리 프레임.
- SOOP은 바이너리 프레임 기준이라, 명시적으로 encode해서 바이트로 보내는 게 안전.

## 4. SOOP 패킷 구조

모든 패킷: `ESC(\x1b) + TAB(\x09) + 서비스코드(4자리) + 길이(6자리 10진수) + "00" + 본문`

### 서비스 코드
| 코드 | 의미 |
|------|------|
| 0000 | 핑 (연결 유지) |
| 0001 | CONNECT (입장) |
| 0002 | JOIN (방 참가) |
| 0005 | **채팅** |
| 0007 | 방송 종료 |

### 구분자 (계층별로 다름 — 이게 제일 헷갈림)
| 표기 | 값 | 역할 |
|------|------|------|
| SEP | `\x0c` | 1차 구분자. 패킷을 큰 필드로 쪼갬 |
| X12 | `\x12` | 쌍과 쌍 사이 |
| X11 | `\x11` | 한 쌍 안에서 키-값 사이 |
| X6 | `\x06` | 옵션 문자열 내부 |

예: `X12 nation_lang X11 ko_KR` = "nation_lang이라는 새 항목, 값은 ko_KR"
- X12 = 항목끼리 구분, X11 = 항목 안에서 키/값 구분

### 값의 출처 (하드코딩 vs API에서)
- **매번 바뀜 → API에서 받음**: CHATNO, FTK (호출마다 새로 발급되는 일회용)
- **고정 → 하드코딩**: `chat`(서브프로토콜), `16`(비로그인 토큰), 구분자, 포트 +1 규칙
- 판단 기준: "매 방송/접속마다 바뀌나?" → 바뀌면 API, 고정이면 코드에 박음

## 5. 채팅(0005) 파싱

`raw.split(b"\x0c")`로 쪼갠 parts의 인덱스:

| 인덱스 | 내용 | 사용 |
|--------|------|------|
| [0] | 헤더 | X |
| [1] | 채팅 내용 | O |
| [2] | 유저 아이디 | O |
| [6] | 닉네임 | O |
| [9][10] | 색상 코드(추정) | - |
| [7] | 비트플래그: 구독/팬/등급(추정) | - |
| 나머지 | -1(미사용) 또는 미해독 | - |

- 쓰는 건 [1], [2], [6] 세 개.
- 나머지는 정확한 의미 미해독. 등급/구독/팬/매니저 여부로 추정.
  필요하면 매니저/구독자 채팅을 비교 관찰하면 알아낼 수 있음.
- **서비스 코드 위치**: `raw[2:6]` ([0]=ESC, [1]=TAB, [2:6]=서비스코드 4자리)

## 6. async / 웹소켓 개념

### async를 쓰는 진짜 기준
- "다른 프로그램이 일하냐"가 아니라 **"기다리는 I/O가 있고, 그 틈에 딴 일을 하고 싶냐"**.
- requests(동기)도 다른 서버를 쓰지만 그동안 파이썬이 멈춤. httpx async는 그 틈에 딴 일 함.

### async 전염성
- `await`는 async 함수 안에서만. async 함수를 부르면 부모도 async가 됨.
- 맨 꼭대기 `asyncio.run()`이 "동기 ↔ async 세계"의 문. 여기엔 await 안 붙임.

### recv vs send가 분리된 이유
- 웹소켓은 요청↔응답이 짝이 아님. 그냥 시간순 녹취록.
- `send`는 보내기만, `recv`는 따로 받기. 서버가 짝을 안 지어줌 → 받아서 서비스코드로 분류.

### CONNECT 다음 sleep(1)이 필요한 이유
- CONNECT랑 JOIN을 연달아 즉시 보내면, 서버가 CONNECT 처리를 끝내기 전에 JOIN이 도착해 무시됨.
- sleep(1)로 시간을 벌어 CONNECT 처리가 끝나게 함. (recv로 응답을 기다리는 방법도 됨)

### ping_interval=None 이 필수인 이유
- websockets 라이브러리는 자체 표준 핑을 20초마다 보냄.
- SOOP은 이 표준 핑을 못 알아들어 응답 안 함 → 라이브러리가 "죽은 연결" 판단하고 **내 쪽에서** 끊음
  (`keepalive ping timeout` 에러, 코드 1011 sent).
- 그래서 표준 핑을 끄고(None), SOOP 전용 핑(0000)을 직접 보냄.

### create_task 결과를 변수에 담는 이유
- ① 나중에 `.cancel()` 하려면 손잡이(변수)가 필요.
- ② asyncio는 태스크를 **약한 참조**로만 들고 있음 → 변수에 안 담으면 GC가
  "아무도 안 붙잡네" 하고 회수할 수 있음 (돌고 있어도!). 회수 시점은 예측 불가.
- 강아지에 목줄(변수) 안 매면 언제 나갈지 모름 → 변수에 담아 확실히 붙잡음.

## 7. SSL (참고)

- `wss://`의 `s`가 SSL/TLS. **주소가 wss면 암호화는 자동으로 켜짐** (설정 안 해도 됨).
- SSL은 두 가지: ① 암호화 ② 신원 확인.
- `check_hostname=False`, `verify_mode=CERT_NONE`은 **② 신원 확인만 끔** (암호화는 유지).
- SOOP 내부 서버는 인증서 이름이 접속 이름과 안 맞아 신원 확인이 실패할 수 있음
  → 그때만 이 완화를 넣음. 지금은 기본값으로 접속되니 불필요.
- 읽기 전용 공개 채팅이라 신원 확인 꺼도 실질 위험 거의 없음.

## 8. 코드 구조 (역할 분리)

- `get_soop_broad_info(bid)` — API에서 방송 정보 받기
- `make_soop_chat_ws_packet(info)` — CONNECT/JOIN/PING 패킷 3개 생성
- `ping_loop(ws, ping_packet)` — 60초마다 핑 (백그라운드 태스크)
- `stream_soop_chats(bid)` — **제너레이터**. 채팅 parts를 하나씩 `yield`.
  연결/핑/종료 관리 + 상태 로그(수신 시작/방송 종료)까지 담당.

소비 방식:
```python
async for parts in stream_soop_chats(bid):
    # parts로 파싱하거나 DB에 저장 (소비자의 몫)
```
- 제너레이터는 "채팅 raw parts 내보내기"만.
- 파싱/저장/화면출력은 **소비하는 쪽(DB 파일)**이 정함.
- 단, "수신 시작 / 방송 종료" 같은 **수집기 상태 로그**는 제너레이터에 둬도 됨 (자기 상태니까).

## 9. 리버스 엔지니어링 방법론 (이번에 익힌 것)

이 프로젝트를 관통한 핵심 기술:

1. **브라우저를 훔쳐본다** — 문서 없어도 "잘 되는 브라우저가 이 순간 뭘 했나"를 개발자도구로 관찰.
   - HTTP: 네트워크 탭에 요청이 통째로 찍힘.
   - 웹소켓: WS 항목 → Messages 탭에 오간 메시지가 시간순으로. ↑=내가 보냄, ↓=서버가 보냄.

2. **값의 출처를 역추적** — 패킷 안의 정체불명 값을 API 응답에서 찾아 매칭.
   - 예: JOIN 패킷의 `b5f08175..._ldrboo_...` → API의 FTK 였음.

3. **최소 요건 찾기** — cURL 통째로 복사 후 한 줄씩 지워가며 진짜 필수만 남김.

4. **안 보이는 문자는 hex/repr로** — `bytes.fromhex()` + `repr(x.decode("latin-1"))`로
   `\x0c` 같은 제어문자를 눈에 보이게. (latin-1은 모든 바이트를 안 깨지고 보여줌)

5. **가설 → 검증** — "이 숫자가 길이일까?" → 값 다른 샘플 비교 → 실제로 세서 확인.

6. **원본과 대조** — 조립한 패킷을 원본 hex와 글자 단위로 비교. 같으면 재현 성공.
