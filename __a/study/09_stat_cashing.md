## 1. 캐시 도구 지형 (Redis 주변) ★

- **캐시 층(같은 역할):** Redis / Valkey / Memcached / Dragonfly.
  - Redis가 표준(인메모리 스토어 점유율 ~82%). Sorted Set 등 자료구조 O.
  - **Valkey** = Redis 라이선스 변경(2024 BSD→소스어베일러블)에 Linux 재단이 포크한
    BSD 대체재. 코드 호환 드롭인. "Redis 대안?"의 현재 첫 답.
  - **Memcached** = 순수 key-value 처리량은 근소 우위(멀티스레드). 근데 자료구조
    없음 → 내 `/stats`의 Sorted Set 순위 못 함. 나한텐 부적합.
- **큐·스트리밍 층(다른 역할):** Redis Streams / **Kafka** / RabbitMQ.
  - **Kafka는 캐시가 아니다.** 메시지 큐/이벤트 스트리밍. 내 Redis Stream과 같은
    역할군. Kafka로 오해해서 "성능 좋은 캐시"로 착각하면 안 됨. 층이 다름.
  - Kafka는 초당 수십만~수백만 이벤트 규모에서 진가. 내 규모(초당 수백~수천)엔 과함.

### 유휴 메모리 비용 (그냥 떠 있는 비용) ★
- **C 계열(Redis/Valkey/Memcached):** 빈 상태 유휴 메모리 한 자릿수 MB. 무시할 만함.
  메모리 먹는 건 "떠 있어서"가 아니라 "내가 넣은 데이터만큼".
- **JVM 계열(Kafka):** 데이터 없어도 힙 수백MB~수GB 잡고 시작. 32GB 미만 비생산적.
  개인 노트북에 얹으면 부하 테스트 중 자원 다툼 → 측정 오염. Redis 하나가 옳은 이유.
- 교훈: **"상황 맞춰 여러 툴 띄우기"는 규모가 정당화할 때 얘기.** 내 규모에선 툴
  늘리는 것 자체가 순비용(메모리·운영 복잡도).

## 2. "인메모리인데 왜 DB랑 비슷하냐" — 이 세션의 출발 의문 ★★

`/stats`(Redis) p95가 인덱스 건 `/chats`(Postgres) p95랑 비슷하게 나옴(둘 다 40ms대).
"인메모리가 이렇게 느릴 리가?" → 파봤더니 전제가 틀림.

### 진짜 답: "인메모리가 안 빠른" 게 아니라 "DB가 (인덱스 덕에) 안 느려진" 것
```
/chats 응답 = [파이프라인 고정비] + [Postgres 인덱스 조회]
/stats 응답 = [파이프라인 고정비] + [Redis 왕복 2번]
```
- 파이프라인 고정비(FastAPI 라우팅·의존성·Pydantic 직렬화·소켓·도커 네트워크)는
  두 엔드포인트가 거의 같음.
- 인덱스 건 Postgres 조회도, Redis 조회도 **둘 다 sub-ms~수 ms로 이미 빠름.**
- → **둘 다 파이프라인 고정비가 지배.** 백엔드 종류(DB/Redis) 차이가 파묻혀 안 보임.
- 비유: KTX(DB+인덱스)나 비행기(Redis)나, 역/공항까지 가고 타고 내리는 고정시간
  붙으면 총 이동시간 비슷. 인덱스 걸기 전 완행열차(85ms)일 땐 차이가 컸음.

### "인메모리가 빠르다"의 정확한 의미 ★
- 틀린 기억: "인메모리 > 디스크" (막연히).
- 정확: **"디스크를 실제로 때리는 작업이 느리다."** 인메모리(Redis)는 디스크→메모리
  옮기기가 원천적으로 없음. 근데 DB도 데이터가 메모리 캐시(shared_buffers)에 있으면
  디스크 안 때림 → 그때는 DB도 사실상 인메모리 조회.
- 층이 셋:
  1. 디스크 진짜 읽음 (느림, 수 ms~수십 ms) — 인덱스 없는 Seq Scan 85ms
  2. DB가 메모리에 캐싱해둠 (빠름, sub-ms) — shared_buffers hit
  3. 아예 항상 메모리에만 (빠름, sub-ms) — Redis
- **2번과 3번은 물리적으로 같은 "RAM 읽기"** → 속도 비슷. 그래서 비슷하게 나온 것.

### 사전 계측으로 확인 (perf_counter / print)
- `stat_ingredient`(Redis 두 왕복)를 print로 재보니 **1~4ms**, 전체 응답은 7~13ms.
  → **응답의 절반 가까이가 Redis 밖.** Redis는 범인의 절반 이하.
- Redis 명령 자체는 `INFO commandstats`의 usec_per_call로 **~1μs**(마이크로초). 즉
  Redis는 응답시간의 0.02%도 안 됨. "느린" 건 그걸 감싼 HTTP 파이프라인.

### 함정: logger.info가 안 찍힌 이유 ★
- `logging.getLogger(__name__)`만 하면 **레벨 미설정 → 기본 WARNING.** INFO는 걸러짐.
  (그래서 services.py의 `logger.warning`은 나오는데 info는 안 나옴.)
- 임시 계측은 그냥 **`print`**가 확실(워커 stdout에 나옴).

## 3. 블록(페이지) — Postgres의 읽기 단위 ★★

### 정체
- **블록 = Postgres가 읽고 쓰는 최소 단위. 기본 8KB.** 디스크든 메모리든 항상 8KB
  통째로 다룸. 행 하나씩이 아님.
- 8KB 블록 하나에 행 여러 개(내 chats 행 ~100~200B면 블록당 40~80행).
- "100만 행 읽는다" = "그 행들이 흩어진 41,346개 블록을 읽는다". 행이 아니라 블록으로 셈.
- **디스크 블록과 메모리 블록은 같은 것.** 하나의 8KB 덩어리가 디스크↔메모리를 오감.

### 인덱스가 블록에 하는 일 ★
- 인덱스는 캐싱 기능이 **아니다**(내가 헷갈렸던 것, 반박이 맞았음).
- 인덱스 = **"어느 블록만 읽으면 되는지" 알려줘서 안 읽어도 될 블록을 안 읽기.**
  - 인덱스 없음: 조건 맞는 행 위치를 모름 → 41,346블록 전부 읽고 대부분 버림(Filter).
  - 인덱스 있음: 지도로 필요한 블록만 콕. **68~104블록.**
- "빨리 읽기"가 아니라 **"적게 읽기"**가 인덱스의 본질.

### LIMIT + 인덱스 = 데이터 크기 무관 ★★
- 68~104블록의 진짜 비밀은 15% 필터가 아니라 **`LIMIT 100`**.
- 복합 인덱스 `(bid, received_at DESC)`는 이미 "bid 구역 안 시간 역순 정렬" 상태.
  → 그 구역 맨 위 100개만 떼면 끝. bid에 행이 9만이든 90만이든 읽는 양 동일.
- 실측: `rows=95483`(매칭 9만5천) 인데 `actual rows=100`, 블록 104개. 데이터 크기
  무관성의 실물. (T4-2 "데이터 크기에 둔감"의 정체.)

## 4. shared_buffers vs Redis — 두 캐시의 차이 ★★

`EXPLAIN (ANALYZE, BUFFERS)`로 직접 봄. **`BUFFERS` 옵션 켜야 hit/read 나옴.**

### read → hit 전환 (직접 관찰)
같은 쿼리 연속 두 번:
```
1회차(콜드): Buffers: hit=11 read=93   Execution 1.529 ms
2회차(웜):   Buffers: hit=104 (read=0) Execution 0.344 ms   ← 4.4배↓
```
- **read** = 디스크에서 새로 읽음(캐시에 없던 것). **hit** = 메모리에서 찾음(캐시된 것).
- 1회차가 올려둔 블록을 2회차가 hit. 이게 shared_buffers 캐싱의 실물.
- 블록당 디스크 vs 메모리 차이 ≈ 13μs (이 환경). 일반론(메모리가 SSD보다 100~1000배)의
  구체값. 근데 68블록이면 차이 작고(sub-ms), 41,346블록이면 수십 ms로 벌어짐 →
  **"적게 읽기(인덱스)"가 "빨리 읽기(캐시)"보다 근본적.**

### 첫 쿼리 느림의 주범 = planning ★
- 1회차: Planning 7.248ms + Execution 1.020ms. 2회차부터 Planning 0.2 → 0.09ms.
- Postgres는 실행 전 **실행계획 수립(planning)** — 통계·카탈로그 블록을 읽음
  (`Planning: read=33`). 세션 첫 쿼리는 이게 콜드라 7ms. 두 번째부터 캐시.
- 부하 테스트에선 첫 요청만 이 비용, 나머지는 캐시 → p95에 안 잡힘.

### 두 캐시의 근본 차이 ★
| | Postgres shared_buffers | Redis |
|---|---|---|
| 캐싱 대상 | DB가 자동 결정(블록) | 앱이 명시(원하는 값) |
| 유지 시간 | 자동(LRU), **제어 불가** | **TTL 직접 지정** |
| 무엇을 저장 | 테이블/인덱스 블록 | 아무 값이나(집계 결과 등) |
| 용도 | DB 조회 자체를 빠르게 | **DB를 아예 안 거치게** |
- shared_buffers는 "블록"만 캐싱 → 쿼리 실행(파싱·집계) 자체는 매번 다시 함.
- Redis는 **최종 결과**를 저장 → 계산 통째로 스킵. 그래서 "무거운 집계"에 강함.
- **Redis 쓰는 이유 = 시간 제어(TTL) + 최종 결과 저장** 둘 다. (내 착각: 시간 제어만인 줄)

## 5. 캐싱 실측 (T4-3) ★★★

### cache-aside 패턴
```python
raw = await r.get(key)                 # ★ await 필수 (안 붙이면 코루틴 반환 → 항상 hit 오판)
if raw is not None:                    # hit
    return GetStatsResponse.model_validate_json(raw)
# miss: 원본 집계 → set
resp = GetStatsResponse(...)
await r.set(key, resp.model_dump_json(), ex=15)   # ex=초 단위 TTL
return resp
```
- **redis.asyncio는 get/set/zrevrange 전부 코루틴 → 예외 없이 `await`.** 반환 여부 무관.
  (이번에 `r.get`에 await 빼먹어서 모든 요청 hit 오판 + 코루틴을 JSON 파싱 → 터짐.)
- **Redis는 list/dict 못 저장 → 직렬화 필요.** 문자열/바이트/숫자만.
- **Pydantic이 편함:** `model_dump_json()`이 datetime까지 자동 직렬화.
  `json.dumps(datetime)`은 TypeError. → 최종 응답(Pydantic) 통째 캐싱이 깔끔.
- **어디에 캐싱?** raw(stat_ingredient 결과, datetime 낌) 말고 **최종 응답**.
  히트 시 Redis 2왕복 + zip 조립 + Pydantic 검증까지 전부 스킵 → 더 많이 건너뜀.

### 측정 결과 (워커8/800/ramp20/ecvhao/TTL15)
| 지표 | off | on |
|---|---|---|
| #reqs | 45,200 | 131,683 |
| p50 | 13ms | 12ms |
| p95 | 41ms | 35ms |
| zrevrange/mget calls | 45,200 각 | **133 각** |
| get/set calls | 0 | 131,692 / 133 |
| 요청당 Redis 명령 | 2.00 | ≈1.00 |
| 원본 집계 호출 | 45,200 | 133 (히트율 99.9%) |

### 핵심 교훈 ★★★
- **응답시간 안 줄음(p95 41→35, 불변).** 캐싱 대상(Redis)이 이미 μs라, 없애봤자 13ms
  응답에서 0.02% 뺀 거. **캐싱이 지연을 줄이려면 대상이 비싸야 함.**
- **명령은 340배 줄음(45,200→133).** 이득이 "지연"이 아니라 **"백엔드 부하 경감"**으로
  나타남. **"응답 안 빨라졌으니 무의미"가 아니라 "지표를 바꿔 봐야" 함.**
- 이 부하 경감은 지금 규모에선 체감 없지만, 초당 수십만 요청이면 Redis(싱글스레드)
  처리량 **천장(capacity)을 올림.** 지연이 아니라 용량을 사는 것.

### INFO commandstats / MONITOR — Redis 관측 도구 ★
- **`INFO commandstats`** = 명령별 누적 호출 수(calls). **부하 측정용 정답**(관측 비용 ~0).
  절차: 런 직전 `CONFIG RESETSTAT`(0으로) → 런 → `INFO commandstats`(차분).
- **`MONITOR`** = 모든 명령 실시간 로그. **부하 중 금지**(Redis 느려짐 = 측정 오염).
  저부하 사전 검증(로직이 의도대로 도나 육안)용.
- Locust는 클라이언트(HTTP)만 봄 → Redis 명령 수는 못 봄. 그래서 위가 필요.

### cache stampede
- 만료 순간 여러 요청이 동시에 miss → 서로 채우기 전에 우르르 원본으로.
- 그래서 miss가 이론상 ~12번(런 187초/TTL15)인데 실측 133번. 규모 작아 무해했음.

## 6. 캐싱 판단 기준 ★★ (이 세션 최대 수확)

**캐싱은 자동으로 좋은 게 아니다. 대가가 있다:**
1. **메모리** — 제일 작음. 캐시 키 수백B~1KB, 다 해도 수 MB. Redis 유휴 비용보다 작음.
   망설일 이유 못 됨.
2. **정확성** — 진짜 대가. 캐싱 = "낡은 값을 잠깐 보여주는 거래". TTL이 그 창.
   잔액·재고처럼 1초도 못 낡는 데이터엔 위험. 내 `/stats`는 "완결된 분만 봄" 로직
   덕에 이 대가가 거의 0이었음.
3. **복잡성** — 눈에 안 보이는 대가. hit/miss 분기, 직렬화, 새 실패 모드(캐시가 틀린
   값 들면?), 무효화 로직. (await 버그가 그 예.) "캐시 무효화는 2대 난제" 농담.

**판단 순서:**
```
① 매번 하기에 비싼가? — 안 비싸면(이미 인메모리) 지연 이득 미미. 대개 여기서 멈춤.
② 비싸면, 부하 경감이 필요한 규모인가?
③ 낡은 값 허용되나? — 안 되면(잔액 등) 캐싱 부적절.
④ TTL 창당 요청 빈도 충분한가? — 손익분기 이상인가.
→ 넷 다 통과할 때만 값어치.
```

### 캐싱 손익분기 ★
- 명령 수: 캐싱 없음 = 2N, 캐싱 있음 = N+3 (miss의 get 허탕 + set 선투자).
- `N+3 < 2N → N > 3`. **TTL 창당 요청 4개 이상**이어야 이득.
- N=1이면 캐싱이 오히려 손해(2 vs 4). 요청 드문 방송엔 캐싱 손해.
- 근데 현실은 Zipf 편향(인기 방송에 요청 몰림) → 전체로는 이득. 인기 방송의 큰 이득이
  소형 방송의 손해를 덮음.

### TTL은 다이얼 ★
- 짧은 TTL = 정확성 대가↓ + 히트율(이득)↓. 공짜로 좋아지는 게 아니라 **정확성↔히트율
  조절 손잡이.** 내 15초 = "정확성 거의 안 해치면서 히트율 99.9%"인 좋은 지점.
- 데이터 성격마다 이 지점이 다름.

### 내 `/stats`는? ★
- ①에서 이미 "아니오"에 가까웠음(워커가 Redis에 실시간 집계 해둬서 그냥 꺼내기만).
- 그래서 캐싱해도 지연 이득 0. **이번 캐싱은 "측정을 위해" 넣은 것.** 실서비스엔
  빼거나, 남기면 "규모 확장 대비" 주석 달기. "넣었다 빼며 판단 기준 세운 것" 자체가 수확.

## 7. Redis 커넥션 풀 — DB 풀과 정반대 ★

- 착각: "Redis도 DB처럼 풀이 병목일 것" → 워커1이 빨랐던 게 "풀 고친 효과"라 오해.
- **틀림.** 워커1이 빨랐던 건 풀 때문이 아니라 **동시 요청이 적어 경합이 없어서.**
- `redis.from_url` 클라이언트는 내부에 커넥션 풀 있고, `max_connections` 미지정 시
  **상한 사실상 무제한(2³¹).** 동시 요청 오면 알아서 커넥션 여러 개 씀.
  → **조정할 풀이 이미 무제한. 늘릴 여지 없음.** (명시하면 오히려 상한 씌워 느려짐.)
- **psycopg(DB)는 정반대:** `max_size` 미지정 시 4로 고정 → T4-1에서 병목이었음.
- **같은 "풀"이라도 라이브러리마다 기본 동작이 정반대.** 반드시 확인.
- Redis 병목의 진짜 후보: 이벤트 루프 경합 / Redis 싱글스레드 처리 직렬화 / CPU 포화
  (커넥션 풀 아님). 커넥션 여러 개의 이득도 "Redis 병렬화"가 아니라 "왕복 대기 겹치기".

## 8. 방송종료 트리거 집계 (리디자인 — 메모, 다음에) ★

이 세션에서 설계만 하고 미룸. `/stats` 롤링 윈도우 로직 완성도 낮아서 바꾸려던 것.

### 발상
- 실시간 집계(현재 `/stats`)는 지금처럼 Redis에서 DB 안 거치고. (hot)
- **방송 종료 시** 확정 집계 계산해서 그날 그 방송인의 집계를 **DB에 롤업 저장.** (cold)
- 방송 도중엔 확정 집계 안 함. design.md 4장 "원본 무한저장 대신 요약만 남긴다"와 정합.

### "프로세스 종료 ≠ 방송 종료" 함정 ★★
- 종료 감지 3갈래: ① in-band(프로듀서가 종료 신호 XADD, `finally`/`atexit`/SIGTERM.
  단 kill -9엔 안 됨) ② heartbeat(TTL 키, 크래시도 잡음, 감지 지연) ③ supervision
  (부모/systemd/도커가 exit 감지, 가장 확실).
- **핵심 함정:** 프로세스는 방송 종료 말고도 네트워크 끊김·배포·OOM으로도 죽음.
  design.md 6.1에 "끊기면 자동 재연결" 있으니, "끊김 → 집계 확정" 걸면 방송 한 번에
  집계 여러 번 튐.
- **답:** 트리거를 "프로세스 죽음"이 아니라 **"방송 종료 이벤트"**에. SOOP이 종료
  코드 **0007**로 알려줌. 단 0007이 방송종료 때만 오는 게 아니라 **3회 재시도**로 확인
  → 종료 마커 XADD → 별도 컨슈머가 집계.
- **멱등성:** 어느 트리거든 집계 두 번 돌 여지 있음. DB 롤업은 `(bid, 날짜)` upsert
  (`ON CONFLICT`)로 멱등하게. design.md 5.3 또 나옴.

### 왜 이게 캐싱과 연결되나 ★
- 날짜/시간 고정 버킷으로 집계하면 **지나간 버킷은 값 불변** → 캐시 영구 가능(롤링
  윈도우의 짧은 TTL 문제 소멸).
- 집계를 Redis 카운터 말고 **원본 chats에서 날짜별 GROUP BY**(100만 행 훑는 무거운
  집계)로 하면 → **캐싱이 T4-2급 이득으로 살아남.** (오늘 캐싱 밋밋했던 이유의 해소책.)
- 즉 리디자인 = "캐싱할 가치 있는 비싼 대상"을 만드는 것.

## 9. 측정 규율 재확인 (이 세션에서 또 어긴 것들) ★

- **`--no-access-log` 계속 안 쓰고 있었음.** 엔드포인트 간 비교(둘 다 켜짐)엔 상쇄돼
  괜찮지만, **절대값 분해(13ms가 왜?)엔 access log가 노이즈로 섞임.** 큰 배수 볼 땐
  무시 가능, 작은 것 쪼갤 땐 제거 필수. **측정 정밀도 요구가 실험마다 다름.**
- **한 번에 한 변수만** — bid를 bid_1→ecvhao로 바꾸면서 유저 수도 같이 바꿔서 비교가
  오염됐던 순간 있었음. off/on은 반드시 같은 bid.
- **어제 테이블을 삭제해서** bid_1이 0행이었음. 실험 전 `SELECT count(*)`로 데이터
  상태 확인. 전제 안 맞으면 이후 전부 무의미.
- **예측을 먼저 박아두기.** "on은 명령 반토막, p95 불변"을 측정 전에 적어두니 결과
  해석이 정직해짐(그리고 명령은 반토막이 아니라 340배라 예측보다 극적 → 그것도 발견).
