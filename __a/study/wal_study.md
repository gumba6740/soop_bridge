# WAL · 커밋 · 원자성/내구성 학습 노트

> PostgreSQL의 쓰기 경로를 따라가며 정리한 노트.
> 핵심 질문: "커밋하면 데이터가 어디에, 어떤 순서로, 얼마나 안전하게 저장되는가?"

---

## 1. 데이터는 어디에 사는가


- **shared_buffers** (메모리) — 디스크의 heap 데이터 파일을 캐시한 구역. 트랜잭션이 행을 바꾸면 **여기 페이지를 직접 수정**한다. 실데이터의 최신본이 여기 먼저 생긴다.
- **heap 데이터 파일** (디스크) — 테이블·인덱스가 실제로 영속되는 파일. shared_buffers의 수정본이 **나중에** 여기로 내려간다.


- **WAL (Write-Ahead Log)** — "데이터에 가한 변경의 기록(redo 로그)". **실데이터가 아니라 변경 이벤트를 순서대로 적은 장부.**
  - 물리적으로는 **디스크 파일**(`pg_wal/` segment들).
  - 다만 앞단에 **WAL buffers(메모리)**를 두고, 거기 잠깐 모았다가 디스크 파일로 내린다.

| 계층 | 위치 | 담는 것 |
|---|---|---|
| shared_buffers | 메모리 | 실데이터(최신본) |
| heap 파일 | 디스크 | 실데이터(영속) |
| WAL buffers | 메모리 | 변경 레코드(임시) |
| WAL 파일 | 디스크 | 변경 레코드(영속) |

---

## 2. INSERT 한 건의 실제 흐름

커밋을 치기 **전에** 이미 다음이 벌어진다:

1. shared_buffers의 데이터 페이지를 수정 → **실데이터가 바뀜**
2. 그 변경을 **WAL에 먼저 기록** (write-ahead)

> **write-ahead의 규칙**: 데이터 페이지가 디스크로 내려가기 *전에* WAL이 반드시 앞서야 한다. 실무적으론 거의 한 몸이지만 순서가 있다.

핵심 반전: **변경은 커밋 여부와 무관하게 이미 물리적으로 존재한다.** 여러 문장을 한 트랜잭션에 넣으면, 커밋 전까지 그 변경 레코드들이 WAL에 차곡차곡 쌓인다.

---

## 3. 커밋 단계 — commit record와 fsync

`COMMIT`이 하는 일:

1. **WAL에 commit record 추가** — "이 트랜잭션(XID)은 여기서 정상 종료됨"이라는 **마침표/도장**.
2. 그 commit record까지 포함한 WAL을 **디스크로 fsync** → 내구적으로 확정.

### commit record는 데이터가 아니다

commit record 안에는 **실데이터가 없다.** 그냥 "이 트랜잭션 유효" 플래그(몇 바이트). 실데이터는 그 앞의 **변경 레코드(heap insert record 등)**에 있다.

```
[트랜잭션 42: 행 A를 X페이지에 삽입]   ← 실데이터 있음
[트랜잭션 42: 행 B를 Y페이지에 삽입]   ← 실데이터 있음
[트랜잭션 42: COMMIT]                  ← 데이터 없음, "42 유효" 도장
```

### 판정 규칙 (all-or-nothing의 근원)

크래시 복구 때 WAL을 재생하며:

- commit record까지 **온전히 디스크에 있음** → 앞의 변경 전부 반영 (**all**)
- commit record **없음/불완전** → 앞의 변경 전부 폐기 (**nothing**)

→ "반쯤 반영"이 원천적으로 안 생긴다. **마침표 하나의 유무로 트랜잭션 전체가 갈린다.**

---

## 4. write() vs fsync() — "쓴다"의 두 단계

파일에 내보내는 데엔 두 동작이 있다:

1. **write()** — Postgres가 내용을 OS에 넘김. 근데 OS는 바로 디스크에 안 박고 **자기 page cache(메모리)에 들고 있음.**
2. **fsync()** — "지금 캐시에 든 걸 **당장 물리 디스크에 확정하라**"고 강제. 이게 끝나야 정전에도 안 사라짐.

→ write만 하면 OS 캐시에만 있어 위험. **커밋이 기다리는 건 fsync 쪽.** `synchronous_commit=off`가 지연시키는 것도 정확히 이 fsync 대기.

---

## 5. 커밋이 확정하는 건 WAL이지 heap이 아니다

반직관적이지만 핵심:

| | 커밋이 디스크에 확정? | 언제 heap 파일 반영? |
|---|---|---|
| **WAL (변경 로그)** | ✅ 커밋 시 fsync | — |
| **heap (실데이터)** | ❌ 커밋이 안 건드림 | 나중에 백그라운드(checkpoint) |

커밋 성공 직후 상태:

```
WAL 파일 (디스크)       : ✅ commit record까지 fsync 완료 = 안전
heap 데이터 파일 (디스크): ❌ 아직 안 내려감 (최신본은 shared_buffers 메모리에만)
```

**실데이터가 디스크 테이블엔 없고 메모리에만 있는데 커밋은 성공**일 수 있다.
안전한 이유 = write-ahead: 크래시 나도 **디스크의 WAL을 재생**하면 heap을 복원할 수 있으니까.

> 커밋이 보장하는 건 "실데이터가 디스크 테이블에 들어갔다"가 아니라
> **"그 변경을 복원할 수 있는 WAL이 디스크에 안전하다"**이다.
> 즉 커밋은 "데이터를 디스크에 넣는" 단계가 아니라 **"이 변경은 이제 안 잃는다고 도장 찍는" 단계.**

---

## 6. 왜 굳이 WAL을 거치나 (WAL도 디스크인데)

"heap에 바로 쓰면 되지 왜 WAL을?" → **WAL fsync가 heap fsync보다 압도적으로 싸기 때문.**

| | heap 직접 쓰기 | WAL 쓰기 |
|---|---|---|
| 위치 | 흩어진 페이지 (테이블+인덱스) | 파일 끝에 append |
| 접근 패턴 | **랜덤 쓰기** (느림) | **순차 쓰기** (빠름) |
| 용량 | 8KB 페이지 여러 개 | 변경 사실만 압축 (작음) |

**트릭**: 매 커밋 = 싸고 작은 **WAL만 fsync(순차)**. 무겁고 흩어진 **heap fsync는 나중에 몰아서(checkpoint)**.
= "작은 걸 순차로 자주" vs "큰 걸 랜덤으로 매번" → 전자가 압도적으로 싸다.

**덤 — group commit**: WAL은 순차 로그라, 몰린 여러 트랜잭션의 WAL을 **한 번의 fsync로 묶어** 확정 가능. heap 직접 쓰기였으면 위치가 흩어져 불가능.

## 7. synchronous_commit on/off — 내구성 노브

`COMMIT` 시 WAL fsync를 **기다리냐 마냐**를 조절.

- **ON (기본)**: commit record가 **디스크에 확정된 걸 확인한 뒤** 커밋 성공 리턴.
  → "성공 리턴 = 진짜 안전"이 항상 참.
- **OFF**: commit record를 **WAL 버퍼(메모리)에만** 넣고 **fsync를 안 기다린 채** 성공 리턴.
  실제 fsync는 백그라운드가 조금 뒤(~수백 ms)에 처리.

### OFF의 위험: "거짓 성공"

커밋이 "성공"이라 리턴한 직후 ~ fsync 전 사이에 크래시하면:
- 그 트랜잭션의 commit record가 디스크에 없음 → 복구 때 **폐기**
- 근데 클라이언트는 이미 "성공"이라 들었음 → **약속 위반 (성공했다던 게 사라짐)**

**단, 정합성은 유지된다.** 사라질 땐 **통째로(nothing)** 사라지지 반쯤 안 남는다.
이미 fsync 끝난 이전 트랜잭션들도 멀쩡. → **잃는 건 최신성이지 정합성이 아니다.**

### `fsync = off`와 혼동 금지

이건 완전히 다른(훨씬 위험한) 노브.

| | `synchronous_commit=off` | `fsync=off` |
|---|---|---|
| 하는 일 | 커밋이 fsync를 **안 기다림** (fsync는 여전히 함) | fsync를 **아예 안 함** |
| 크래시 시 | 최근 커밋 몇 개 유실 | **DB 파일 손상 가능** |
| 정합성 | 유지 | 깨질 수 있음 |
| 실무 | 로그성·재수집 가능 데이터에 고려할 만함 | 사실상 금지 |

## 8. 원자성(A) vs 내구성(D) — 직교하는 두 축

가장 중요한 정리. 둘은 **서로 다른 질문**에 답하는 독립 축.

| | 원자성 (A) | 내구성 (D) |
|---|---|---|
| 답하는 질문 | 전부 반영 or 전무? (반쯤 없음) | 성공이라 한 게 크래시에도 살아남나? |
| 보장 장치 | WAL의 **commit-record 유무 → all/nothing 재생 규칙** | WAL을 **fsync로 디스크에 확정** |
| 층위 | 논리적 정합성 | 물리적 영속성 |
| `sync=off`가 건드리나? | ❌ 안 건드림 | ✅ 약화 |

- **원자성** = 로직 층위. 데이터가 물리적으로 어디 있든(메모리/디스크/WAL), 최종 결과가 **all이나 nothing 중 하나로만** 떨어지면 만족.
- **내구성** = 물리 층위. WAL buffer → write → OS 캐시 → fsync → 디스크. 이 흐름을 **어디까지 밀어붙였나.**

**fsync는 원자성을 *만들지* 않는다.** all/nothing 중 어디로 떨어질지 가르는 스위치일 뿐:
- fsync로 commit record 확정 성공 → all
- 확정 전 크래시 → nothing
→ 둘 다 원자적. 원자성은 fsync 이전에 이미 구조적으로 보장돼 있음.

> 원자성 = "기록을 어디서 멈추느냐"가 아니라
> **"이미 여기저기 남은 기록 중 무엇을 유효로 인정하느냐"의 문제.** 그 기준이 commit record.

---

## 9. "원자성이 깨진다"의 진짜 의미

흔한 오해: "원자성이 깨지면 WAL/shared_buffers에 기록이 안 되는 것" → **틀림.**

**부분 기록은 정상 동작에서도 늘 남는다.** INSERT 실행 순간 shared_buffers + WAL 버퍼에 이미 변경이 올라간다(커밋 전에도). 원자성은 그걸 **막는** 게 아니라 **무효화·비가시화**하는 계약:

- **WAL 쪽**: 변경 레코드는 남아 있지만 commit record가 없으면 → 재생 때 폐기. "있지만 없는 것."
- **shared_buffers 쪽**: 롤백이 되감음. (MVCC라서, 죽은 XID가 찍힌 행은 다른 트랜잭션에게 **안 보이고**, 나중에 VACUUM이 실제로 치움.)

→ 질문 "WAL까지 가나 shared_buffers까지 가나"의 답: **둘 다 이미 간다.** commit record라는 도장이 없으면 그 기록들이 "무효"로 처리될 뿐.

"원자성이 깨진 상태" = **부분 반영이 결과에 보이는 것.** Postgres는 WAL+commit record 규칙으로 이걸 원천 차단한다.

## 10. 실패의 종류와 판정 기준

"실패"는 두 갈래. `sync=off`는 그중 **하나에만** 영향.

### (1) 실행 중 오류 (제약 위반·데드락·문법 오류 등)

- `sync` 설정과 **무관.** 커밋 시도 전에 나는 실패.
- 즉시 **abort → rollback.** 변경은 이미 올라가 있지만 commit record가 안 붙어 무효화.
- 클라이언트는 **"실패"** 응답을 받음 → 정직함.

### (2) 커밋은 "성공" 리턴됐는데 fsync 전 크래시

- `sync=off`가 위험을 만드는 유일한 케이스.
- **롤백(능동적 되감기)이 아니다.** 복구 때 commit record가 없어서 **"애초에 없던 일로" 폐기**되는 것.
- 클라이언트는 **"성공"**이라 들었음 → **거짓 성공.**

| | 롤백 (종류 1) | sync=off 유실 (종류 2) |
|---|---|---|
| 클라이언트 응답 | "실패" | **"성공"** |
| 벌어지는 일 | 능동적 되감기 | 복구 때 무시됨 |
| 성격 | 정상 동작 | 약속 위반 (거짓 성공) |

### 최종 판정 기준

"commit record가 만들어졌나"가 아니라 **"commit record가 *디스크에 fsync됐나*"**:

| 상태 | commit record | 결과 |
|---|---|---|
| 롤백/abort | 아예 안 만들어짐 | 폐기 (nothing) |
| 커밋 쳤지만 fsync 전 크래시 | 메모리엔 있으나 디스크엔 없음 | 폐기 (nothing) |
| 커밋 + fsync 완료 | 디스크에 확정 | 반영 (all) |

## 11. 곁가지: fsyncgate (2018)

원자성은 "fsync가 실패하면 **정직하게 실패라고 말해준다**"를 전제로 깐다. 그 전제가 깨진 사건.

- 옛 리눅스 커널: fsync 실패 시 못 내려간 dirty page를 **"깨끗한 걸로 표시"하고 에러를 한 번만 보고한 뒤 버림.**
- Postgres가 실패를 보고 **재시도하면**, 커널은 이미 버려서 **"성공"이라 응답** → 안 내려간 데이터를 내려간 걸로 **오인** → 유실·손상 위험.
- 상위 로직이 완벽해도 **OS 계층의 거짓말**로 보장이 무너질 수 있었던 케이스.

**대응**: 이후 Postgres는 fsync 실패 시 재시도로 얼버무리지 않고 **아예 패닉(crash)내서 WAL 복구 모드로** 진입. ("확정 못 한 걸 확정한 척하느니 죽고 다시 복구.") 리눅스도 에러 리포팅 개선.

→ 교훈: "fsync 실패는 원자성과 무관"은 **설계 의도상 맞지만**, 그 무관함은 "실패가 실패로 제대로 보고된다"는 하부 계약 위에서만 성립한다.

## 1부 요약 (WAL · 커밋 · 원자성/내구성)

- 데이터는 **shared_buffers(메모리) → heap(디스크)**. WAL은 그 변경의 **로그**(디스크 파일 + 메모리 버퍼).
- INSERT는 커밋 전에 이미 shared_buffers + WAL에 **변경을 남긴다.**
- 커밋 = WAL에 **commit record(도장)** 추가 + **fsync로 확정.** commit record엔 데이터가 없다.
- 커밋이 확정하는 건 **WAL이지 heap이 아니다.** heap은 나중에 checkpoint가 내림. 안전한 이유는 WAL 재생으로 복원 가능하기 때문.
- WAL을 거치는 이유: **순차·소량이라 fsync가 싸다.** heap 직접 쓰기는 랜덤·대량이라 비쌈.
- `synchronous_commit=off` = **내구성만** 약화(최근 커밋 유실 가능), **원자성·정합성은 유지.** `fsync=off`와는 전혀 다름.
- **원자성 = commit-record all/nothing 규칙**(논리). **내구성 = fsync**(물리). 둘은 직교.
- 부분 기록은 늘 남는다. 원자성은 그걸 **막는 게 아니라 무효화**한다. 판정 기준은 **commit record가 디스크에 fsync됐는가.**

---

## 12. 롤백이란 무엇인가

흔한 오해: "롤백 = 디스크에 썼다가 물리적으로 삭제." → PostgreSQL에선 **틀림.** "롤백"이라는 한 단어가 사실 두 상황을 가리킨다.

### 상황 1 — 실행 중 명시적 롤백 / abort (커밋 전) = 진짜 "롤백"

`ROLLBACK`을 쳤거나 제약 위반으로 abort된 경우. 변경은 이미 shared_buffers(+WAL 버퍼)에 올라가 있지만, 없애는 방식이 물리 삭제가 아니다:

- INSERT한 행엔 "만든 트랜잭션 XID"가 찍혀 있음.
- 롤백되면 그 XID가 **"실패"로 표시** → 그 행은 다른 트랜잭션에게 **안 보이는 죽은 행(dead tuple)**이 됨. 물리적으론 아직 남아 있음.
- 실제 물리 제거는 나중에 **VACUUM**이 청소.

→ "삭제"가 아니라 **"실패 도장 → 안 보이게 → 나중 청소".** 그리고 커밋 전이면 대개 **디스크 heap엔 아직 안 내려가 있어서** 지울 것 자체가 없을 때가 많음.

### 상황 2 — 크래시로 인한 폐기 (엄밀히는 "롤백" 아님)

서버가 갑자기 죽으면 `ROLLBACK`을 실행할 주체가 없음. 대신 재기동 복구가 **commit record 없는 트랜잭션을 그냥 반영 안 함**(수동적 무시). 이건 능동적 되감기가 아니라 "확정 안 된 걸 안 한 채로 두는" 것.

| | 실행 중 롤백 (상황 1) | 크래시 폐기 (상황 2) |
|---|---|---|
| 언제 | ROLLBACK/abort | 커밋 후 크래시 등 |
| 디스크 heap에 썼나 | 대개 안 씀(메모리에만), 썼어도 dead 표시 | 안 씀 |
| 없애는 방식 | XID로 무효화 + VACUUM 청소 | 복구 때 무시 |
| 능동적인가 | 능동(롤백 실행) | 수동(그냥 안 나타남) |

> 오해 교정 포인트: "썼다가 삭제"는 단순화된 그림. PostgreSQL의 MVCC+WAL에선 ① 커밋 전엔 대개 디스크가 아니라 메모리에만 있고, ② 삭제도 즉시 물리 삭제가 아니라 무효 표시 + 나중 VACUUM 청소다.

## 13. sync=off와 내구성 — "지켜진다/안 지켜진다"가 아니라 "정도"

`sync=off`면 내구성이 완전히 사라지는 게 아니라 **약해진다.** 정확히는 **"성공 리턴 ~ 백그라운드 fsync 완료 사이(수백 ms 창)"에 크래시가 겹친 최근 커밋만** 유실 위험. 그 창 밖(이미 fsync된) 커밋은 여전히 완벽히 내구적.

```
시간축 →→→→→→→→→→→→→→→→→→ [크래시]
[이미 fsync된 커밋들]      [성공 리턴됐지만 아직 fsync 안 된 최근 커밋들]
   ✅ 안전                          ⚠️ 이 꼬리만 유실 위험
```

| 설정 | 내구성 강도 | 크래시 시 잃는 것 |
|---|---|---|
| `synchronous_commit=on` | 완전 | 없음 |
| `synchronous_commit=off` | 부분 | 최근 ~수백 ms치 커밋 |
| `fsync=off` | 거의 없음 + 정합성도 위험 | DB 파일 손상 가능 |

- fsync를 **안 하는** 게 아니라 **안 기다리는** 것 → 크래시만 안 나면 결국 다 내려가 100% 내구적.
- 잃어도 **통째로(nothing)** 잃음 → **원자성·정합성 유지.** 잃는 건 최신성이지 정합성이 아님.
- **합리적인 경우**: 재수집·재처리 가능한 데이터(채팅 등). worker의 `ON CONFLICT DO NOTHING` 멱등성과 함께 쓰면 재처리해도 중복 안 쌓임. **금융·주문 확정엔 부적합.**

## 14. 크래시란 무엇인가

**정상 종료 절차를 못 밟고 갑자기 멈춰서, 메모리에만 있던 미확정 데이터가 디스크로 못 내려간 사건.** "하드웨어적"이냐가 기준이 아님:

- 정전 / 전원 차단
- 커널 패닉 / OS 다운
- 프로세스 강제 종료 (`kill -9`, OOM killer, 세그폴트)
- 하드웨어 고장 (디스크·전원·메모리)
- 컨테이너 강제 종료

공통점 = **메모리에 있던 미확정 데이터의 유실.** 그래서 `kill -9`(SW)도 정전(HW)도 다 크래시.

> **정상 종료(graceful shutdown)는 크래시가 아니다.** 종료 전 checkpoint로 dirty page·WAL을 다 내리고 나가므로, `sync=off`여도 안 잃는다. 위험은 오직 "갑작스러운" 죽음에만.

## 15. on vs off의 진짜 차이 — 유실이 아니라 "거짓말"

fsync 직전 크래시면 **on/off 둘 다 그 데이터를 물리적으로 유실**한다. 물리적 유실 자체엔 차이가 없다. 다른 건 **"성공"을 언제 말하느냐:**

- **on**: fsync 완료 **확인 후** 성공 리턴 → 크래시가 성공 리턴 **전**에 옴 → 클라이언트는 성공을 **못 들음** → "안 됐구나, 재시도" → **앞뒤 맞음.**
- **off**: fsync **전에** 성공 리턴 → 크래시가 성공 리턴 **후**에 옴 → 클라이언트는 성공을 **들었음** → 근데 데이터는 없음 → **거짓 성공.**

| | on | off |
|---|---|---|
| 크래시 시 유실? | 유실됨 | 유실됨 |
| 클라이언트 응답 | 실패/무응답 | **"성공"** |
| 인식 vs 현실 | 일치 | **불일치** |
| 성격 | 정상(재시도 가능) | 거짓 성공 |

> **내구성의 진짜 약속 = "데이터가 절대 안 사라진다"가 아니라 "내가 성공이라 말했으면 그건 진짜다".**
> on은 이걸 항상 지킴(성공=이미 안전). off는 최근 꼬리에서만 이 약속에 구멍.
> 즉 on에서 유실되는 건 늘 "성공이라 말한 적 없는" 커밋뿐 → 그건 유실이 아니라 실패다.

### fsync "재시도" 관련 오해 교정

두 개의 다른 개념이 섞이기 쉬움:

- **개념 A (fsyncgate)**: fsync를 **호출했는데 OS가 실패 반환** → 재시도 말고 패닉. **sync on/off와 무관**(off도 fsync는 함).
- **개념 B (sync=off 유실)**: fsync **호출 전에** 크래시 → 메모리 증발. **재시도할 대상 자체가 없음.** "뭘 재시도할지 몰라서"가 아니라 "확정을 미룬 틈에 죽어서".

→ sync=off 유실은 **실패 처리 문제가 아니라 타이밍 문제.**

## 16. 내구성을 떠받치는 여러 겹 (fsync가 유일이 아니다)

내구성 = "성공이면 안 사라짐". fsync는 그중 **"물리 확정" 한 겹**일 뿐.

| 층위 | 내구성 기여 |
|---|---|
| **WAL 설계** | "먼저 로그" → 복원 가능성의 근원 (진짜 뼈대) |
| **fsync / wal_sync_method** | 메모리 → 물리 디스크 확정 (fsync/fdatasync/open_datasync 등 여러 방식) |
| **크래시 복구(replay)** | 저장된 WAL을 heap에 재적용 |
| **checkpoint** | 복구를 실용적 시간 안에 유지 |
| **디스크 write cache 정책** | fsync 명령이 진짜 물리 매체에 닿게 (배터리/커패시터 백업 등) |
| **복제(replication)** | WAL을 다른 장비로 → 단일 장애점 제거. `synchronous_standby`는 단일 fsync보다 강한 내구성 |

### WAL은 "속도"만이 아니라 "원자성·복구"도 같이 사준다

- WAL 없이도 내구성 구현은 **원리적으로 가능**(예: 매 커밋 heap 직접 fsync, shadow paging). 즉 WAL은 내구성의 정의가 아니라 **선택된 전략.**
- WAL을 쓰는 이유 = **순차·소량이라 fsync가 싸다**(맞음) **+ 원자성·복구까지 같은 로그로 공짜로 얻는다**(핵심).
- heap 직접 fsync는 페이지 3개 중 2개만 내려간 **반쪽 상태**가 디스크에 남아 원자성이 깨질 수 있음. WAL은 commit record all/nothing으로 이걸 원천 차단.

| WAL이 한 번에 사주는 것 | 어떻게 |
|---|---|
| 성능(내구성을 싸게) | 작은 로그를 순차 fsync |
| 원자성 | commit record 유무 → all/nothing |
| 복구 가능성 | 로그 재생으로 heap 재구성 |

## 17. 일관성 (Consistency, C)

### 정의

트랜잭션은 DB를 **하나의 유효한 상태 → 또 다른 유효한 상태**로 옮긴다. 커밋 후엔 **모든 규칙(제약)이 만족**돼야 함. "유효"를 정하는 규칙 = `NOT NULL`·`UNIQUE`·`CHECK`·**FK**·PK·트리거·앱 불변식(예: "잔고 합 일정").

DB는 규칙을 어기는 커밋을 **거부(abort)**해서 일관성을 지킴.

### C는 좀 "얹혀 있는" 개념

C는 독립 실체가 약함. 대부분 **다른 셋 + 선언한 제약**의 결과로 나옴:

- **원자성**이 반쪽 반영 막음 → 반쪽 때문에 규칙 깨지는 것 방지
- **고립성**이 동시 실행 간섭 막음
- **제약/트리거**가 위반 커밋 거부
- → 합쳐지면 일관성이 따라옴

그래서 **DB(제약 강제) + 개발자(올바른 트랜잭션 로직)의 공동 책임.** 규칙을 잘못 선언하거나 로직이 틀리면 ACID를 다 지켜도 "일관"되지 않을 수 있음.

> 주의: ACID의 C는 **CAP 정리의 C(모든 노드가 같은 값)와 다른 개념.** 이름만 같음.

## 18. 고립성 (Isolation, I)

### 정의

동시에 도는 여러 트랜잭션이 **각자 혼자 순차 실행되는 것처럼** 보이게 격리. 서로의 미완성 중간 상태를 안 보게.

실무에서 가장 자주 튜닝하는 축 — **"엄격하게(안전, 느림) vs 느슨하게(빠름, 이상현상)"의 트레이드오프를 레벨로 고름.**

### 느슨할 때 생기는 이상현상

- **Dirty Read**: 아직 커밋 안 한 변경을 읽음. 걔가 롤백하면 유령 데이터.
- **Non-repeatable Read**: 같은 행 두 번 읽는 사이 남이 **수정·커밋** → 값 달라짐.
- **Phantom Read**: 같은 조건 두 번 조회하는 사이 남이 **행 추가·삭제** → 결과 집합 달라짐.
- **Lost Update / Write Skew**: 쓰기 관련 이상.

### 표준 고립 수준

| 레벨 | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| Read Uncommitted | 가능 | 가능 | 가능 |
| Read Committed | 막음 | 가능 | 가능 |
| Repeatable Read | 막음 | 막음 | 가능(표준상) |
| Serializable | 막음 | 막음 | 막음 |

### PostgreSQL의 실제

- 기본 = **Read Committed**.
- **Repeatable Read**: MVCC 덕에 표준보다 강해서 **팬텀까지 대부분 막음.**
- **Serializable**: SSI(Serializable Snapshot Isolation). 충돌 감지 시 한 트랜잭션을 **에러로 abort**시켜 순차 실행과 동일 결과 보장.

## 19. MVCC와 스냅샷

### 관계

- **MVCC**: 행을 수정하면 덮어쓰지 않고 **새 버전을 만듦** → 한 행의 여러 버전이 물리적으로 공존.
- **스냅샷**: 그 여러 버전 중 **"이 트랜잭션에게 뭐가 보이는가"를 정하는 기준선.**
- → MVCC가 버전을 **만들고**, 스냅샷이 **고른다.**

### 스냅샷이 언제 찍히나 = 고립 수준의 정의

"쿼리마다 생기나?"의 답은 **레벨에 따라 다름:**

| 고립 수준 | 스냅샷을 언제 | 결과 |
|---|---|---|
| Read Committed (기본) | **문장(statement)마다 새로** | 쿼리마다 최신 커밋 반영 → non-repeatable 가능 |
| Repeatable Read | **트랜잭션 첫 쿼리에 한 번**, 끝까지 유지 | 트랜잭션 내내 같은 값 |
| Serializable | 위 + 충돌 감지(SSI) | 순차 실행과 동일 보장 |

→ "쿼리마다 스냅샷"은 **기본(Read Committed) 레벨 한정으로 맞다.** 더 엄격한 레벨은 트랜잭션당 하나로 고정.

> 정밀히: BEGIN 순간이 아니라 트랜잭션 안의 **첫 실제 쿼리** 시점에 확정.

---

## 20. MVCC의 "시계" — XID와 xmin/xmax

버전은 **테이블이 아니라 행(튜플) 단위.** 안 바뀐 행은 버전 하나. UPDATE = 새 버전 삽입 + 옛 버전에 죽음 표시. DELETE = 죽음 표시만. 물리 청소는 VACUUM.

"이전 시점 스냅샷을 보여주려면 시간 기록이 필요" → 맞음. 근데 그 시간은 **벽시계가 아니라 XID.**

- **XID**: 트랜잭션마다 발급되는 **단조 증가 정수** = 논리적 시계. (벽시계는 되감기·노드 차이로 불안정, XID는 순서 확실.)
- 각 튜플의 숨은 도장:
  - **xmin** = 이 버전을 **만든** XID (태어난 시점)
  - **xmax** = 이 버전을 **지운/대체한** XID (죽은 시점; 살아있으면 비어 있음)
- → 각 버전은 "XID 몇 번부터 몇 번까지 유효"라는 **생애 구간**을 가짐.

### 스냅샷 = "어떤 XID까지가 커밋된 세계인가" + 진행중 명단

가시성 판정 규칙(개념):

> 어떤 버전이 보이려면 —
> - **xmin이 내 스냅샷 기준 이미 커밋됨** (태어났고 확정) **그리고**
> - **xmax가 없거나 / 아직 커밋 안 됐거나 / 내 스냅샷 이후** (아직 안 죽음)

남이 방금 만든 새 버전은 그 xmin이 내 스냅샷엔 "진행 중/미래"라 **안 보이고**, 나는 옛 버전을 계속 봄. = "이전 시점 스냅샷"의 실제 구현. 시간 여행이 아니라 **XID 도장을 명단과 대조.**

> 더 파볼 곁가지: ① XID는 32비트라 언젠가 한 바퀴(wraparound) → VACUUM이 방지. ② xmin/xmax만으론 "그 XID가 커밋됐는지" 모름 → 커밋 여부를 보는 별도 장치 **clog(commit log)** 필요.

## 21. MVCC vs 잠금 — 역할 분담

MVCC의 주 무대는 **읽기-쓰기 관계.** 동시성 전체를 혼자 처리하는 게 아니다.

| 관계 | 누가 처리 | 결과 |
|---|---|---|
| 읽기 ↔ 읽기 | 자명 | 충돌 없음 |
| **읽기 ↔ 쓰기** | **MVCC** (버전 분리) | 안 막음. 읽는 쪽 옛 버전 / 쓰는 쪽 새 버전 |
| **쓰기 ↔ 쓰기** | **잠금 (row lock)** | 같은 행이면 직렬화(대기) |

- MVCC 핵심 문구: **읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다.**
- **같은 행 쓰기-쓰기 충돌은 MVCC가 무력** → 행 잠금이 나서서 A 커밋/롤백까지 B 대기. "쓰기만 따지면 MVCC가 하는 일 없다"는 이 관계 한정 맞음.
- 단, **쓰기 트랜잭션도 실행 중 읽기 국면**(UPDATE의 WHERE 탐색 등)엔 MVCC를 씀.
- **write skew**: 둘이 서로 다른 행을 쓰는데 각자 옛 스냅샷 보고 결정 → 합치면 규칙 깨짐. MVCC(읽기-쓰기)도 행 잠금(같은 행 아님)도 못 잡음 → **Serializable(SSI)이 필요한 대표 사례.**

→ 실제 동시성 = **MVCC(읽기-쓰기) + 잠금(쓰기-쓰기)** 의 협업.

## 2부 요약

- **롤백**(커밋 전) = 물리 삭제가 아니라 **XID 무효 표시 + VACUUM 청소.** 커밋 전이면 대개 디스크엔 안 내려가 있음. **크래시 폐기**는 롤백이 아니라 "commit record 없어 복구 때 무시".
- **sync=off**는 내구성을 끄는 게 아니라 **최근 꼬리 창만** 위험하게 함. 원자성·정합성은 유지.
- **크래시** = 정상 종료 못 밟은 갑작스런 죽음(정전, kill -9, 패닉…). graceful shutdown은 크래시 아님.
- **on vs off의 차이 = 물리 유실이 아니라 "거짓 성공" 가능성.** 내구성 = "성공이라 한 건 안 잃음".
- **내구성은 fsync 하나가 아니라** WAL 설계 + 확정 수단 + 복구 + checkpoint + 디스크 캐시 + 복제의 여러 겹. WAL은 속도뿐 아니라 **원자성·복구까지 통합**해서 선택됨.
- **C(일관성)** = 유효 상태 유지. A·I·D + 제약 + 개발자의 공동 결과("얹혀 있는" 개념). CAP의 C와 다름.
- **I(고립성)** = 동시 실행을 순차처럼. 레벨로 트레이드오프 조절. 이상현상(dirty/non-repeatable/phantom). PostgreSQL 기본 Read Committed, RR은 팬텀도 대부분 막음, Serializable=SSI.
- **MVCC** = 행 단위 여러 버전. **스냅샷**이 가시성 기준선. 스냅샷 시점 = 고립 수준의 정의(RC=문장마다, RR/Serializable=트랜잭션당 하나).
- **시계는 XID**(단조 증가 정수). 튜플에 **xmin/xmax** 도장 → 스냅샷과 대조해 가시성 판정.
- **MVCC는 읽기-쓰기 비차단용**, 쓰기-쓰기는 **잠금**이 직렬화. write skew는 **SSI** 필요.
