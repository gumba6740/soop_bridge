## 1. 연결을 아끼는 핵심은 "읽기 방식"이 아니라 "읽는 놈의 수" ★★

리디자인 초반의 가장 큰 오해 정정.

- **틀린 생각:** "pub/sub으로 바꾸면 연결이 절약되나?" → pub/sub도 Redis를 쓰고
  구독이 연결을 잡는다. **읽기 방식(xread vs pub/sub)은 연결 수와 무관.**
- **맞는 것:** 절약의 핵심은 **읽는 주체를 1개로 모으는 것.** 구독자 800명이 각자
  읽던 걸 → 리더 1개가 읽고 → 앱 내부에서 800명에 배분. 그러면 유저가 몇이든 Redis
  연결은 리더의 1개.
- xread든 pub/sub든 "리더 1개가 읽어 앱 내부 배분"이라는 구조는 동일. 바뀌는 건 리더가
  그 연결로 뭘 호출하냐(`xread` vs `subscribe`)뿐. 어느 쪽이든 리더 1개면 연결 1개.

### stream 유지가 나은 이유 (이번 선택)
- 프로듀서가 이미 XADD로 stream을 채우고 있음 → 리더가 tail만 하면 **프로듀서 코드 0줄
  수정.** pub/sub으로 가면 "그 채널에 누가 PUBLISH하나"라는 새 손이 생김.
- 중계 리더는 persistence·재처리가 필요 없지만(라이브만 있으면 됨), 코드 수정 최소화가
  더 커서 stream tail 유지.

## 2. 리더는 return도 yield도 안 한다 — "능동적으로 민다" ★★

이 세션 최대의 발상 전환.

- **막혔던 지점:** "리더가 읽은 resp를 어떻게 가져다 쓰지? return? yield?"
- **정답: 둘 다 아님.** return/yield는 "호출한 쪽이 결과를 받는" 모양인데, 리더는
  호출당하는 함수가 아니라 **혼자 무한루프 도는 태스크**다. 받아갈 호출자가 없다.
- 리더가 밖으로 내보내지 않고 **자기 루프 안에서 직접 유저 ws에 send**해버린다.
  지금 `stream_chats`가 하던 `await ws.send_text(chat)`을, ws 하나가 아니라
  레지스트리에서 꺼낸 전원에게 하는 것.

```python
async def reader(app):
    while True:
        resp = await r.xread({key: last_id}, block=1000)
        # ... 채팅 뽑고 ...
        for ws in list(rg.get(bid, set())):   # 레지스트리에서 전원
            try:
                await ws.send_text(chat)       # 직접 민다. return 없음.
            except Exception:
                pass
```

### yield(제너레이터)로도 되지만 안 하는 이유
- `yield bid, chat` 하고 `async for`로 받는 소비자를 또 만들면 되긴 함. 근데 그 소비자
  태스크를 또 만들어 붙여야 해서 **둘로 쪼갠 이득이 없음.** 소비자가 딱 하나(레지스트리에
  뿌리기)라 분리할 이유가 없다. yield는 소비자가 여럿이거나 소비 방식이 다양할 때 빛남.

## 3. 레지스트리 = 그냥 파이썬 dict, app.state에 둠 ★

- 레지스트리는 Redis도 뭐도 아닌 **앱 메모리의 파이썬 딕셔너리.** `dict[bid, set[ws]]`.
- **리더도 이 dict를 보고, `/live` 핸들러도 이 dict를 본다.** 서로 다른 실행 흐름이
  같은 변수를 건드림 → `app.state.registry`에 둬야 둘 다 접근 가능.
  - 핸들러: 접속 시 `rg.setdefault(bid, set()).add(ws)`, 끊기면 `rg[bid].remove(ws)`.
  - 리더: `rg[bid]`를 읽어 전원에게 send.
- 예전에 "리스트에 ws 저장해서 여러 개에 쏴주던" 그 경험과 같음. 달라진 건 쏴주는
  주체가 리더로 분리됐고, 저장소가 app.state로 올라간 것.

## 4. asyncio: 싱글 스레드인데 왜 "동시" 수정 문제가 나나 ★★

- asyncio는 싱글 스레드 → 진짜 물리적 동시 실행은 없음. 근데 **`await`이 흐름을 넘긴다.**
- `await ws.send_text(chat)`은 "보낼 때까지 여기서 흐름을 내려놓고 잔다"는 뜻. 그 틈에
  이벤트 루프가 다른 태스크(다른 유저의 `/live` 핸들러)를 실행 → 그 핸들러가 같은
  set에 add/remove.
- "동시"가 아니라 **"번갈아(interleaving)"**인데, 결과적으로 리더가 순회하는 도중
  목록이 바뀜 → `RuntimeError: Set changed size during iteration`.

### 표현식(expression) 개념 (곁다리로 확실히 잡음)
- 표현식 = **평가하면 값 하나로 귀결되는 것.** "계산식"이 아님(계산 없어도 됨).
  `True`, `42`, `"x"`, `bid == "abc"`, `r.xread(...)` 전부 값이 되므로 표현식.
- 판별법: **다른 것 안에 값으로 끼워넣을 수 있나?** `print("x")` OK → "x"는 표현식.
  `y = (x = "x")` → SyntaxError → `x = "x"`는 표현식 아님(문/statement).
- `x = "x"`에서 우변 `"x"`는 표현식, 전체는 문. **표현식이 문 안에 들어있는** 구조.
- `await r.xread(...)`도 표현식(평가하면 xread 결과값). 단 **평가에 시간이 걸릴 수
  있고, 그 기다리는 순간에 asyncio가 흐름을 넘긴다** — 이게 4번의 핵심.

## 5. 순회 중 변경 방어 — list()로 스냅샷 + try/except ★

두 겹의 방어. 둘 다 있어야 리더가 안 죽는다.

- **`list(rg.get(bid, set()))` — "한 겹"의 정체는 사본(스냅샷).** set을 새로 만들라는
  게 아니라, 순회 직전에 그 순간 원소들을 새 리스트에 복사. 리더는 이 사본을 돌고,
  핸들러가 원본을 고쳐도 사본은 안 바뀜 → "순회 중 크기 변경" 에러 방지.
  - 채팅이 올 때마다(바깥 while 한 바퀴마다) 새 스냅샷을 뜬다. O(구독자 수) 복사 비용은
    이 규모(수백~수천)에선 무시. 정확성 우선.
- **`try/except`로 send 감싸기 — 사본에 남은 죽은 ws 대비.** 스냅샷 뜬 직후 유저가
  끊기면 그 ws가 사본에 남아있어 send가 예외. 리더가 죽으면 **모든** 유저 중계가
  끊기므로, 개별 유저 문제에 리더가 안 죽게 감싼다.

## 6. lifespan에 백그라운드 태스크 띄우기 ★

```python
@asynccontextmanager
async def lifespan(app):
    async with (...):
        app.state.registry = {}
        task = asyncio.create_task(reader(app))   # 백그라운드로 띄움
        try:
            yield                                 # 앱이 사는 동안
        finally:
            task.cancel()                         # 끌 때 정리
```

- **`create_task` vs `await`:** `await reader(app)`이면 무한루프에 갇혀 yield 아래로
  못 내려감(앱이 안 뜸). `create_task`는 "백그라운드에서 돌려두고 나는 계속 진행" →
  리더는 따로 돌고 앱은 정상 기동.
- `yield` 위 = 시작 시 실행, `yield` 아래 = 종료 시 실행. 리더처럼 "앱 수명 내내 도는
  일"은 여기가 교과서적 위치.

### 왜 lifespan이 정답인가 (다른 방법과 비교)
- 리더의 생명주기가 **정확히 앱의 생명주기와 같아야** 함(앱 뜰 때 뜨고, 죽을 때 죽고).
  lifespan은 그 "앱과 생사를 함께"를 표현하는 전용 자리.
- 모듈 로드 시 create_task → 이벤트 루프 없을 때 실행 위험. 첫 요청 때 lazy → 상태
  관리·경쟁 조건. 별도 프로세스 → 더 강력하나 pub/sub 전파 계층 필요(과함). 대안들은
  lifespan이 공짜로 주는 생명주기 결합을 수동으로 다시 만드는 것.

## 7. `receive_text`의 진짜 역할 — 대기 지점 + 끊김 감지 ★

`/live` 핸들러의 `while True: await ws.receive_text()`.

- **받은 텍스트를 쓰려는 게 아님**(유저가 보낸 건 버림). 두 역할:
  1. **연결을 붙잡는 대기 지점.** 핸들러가 등록만 하고 return하면 FastAPI가 "핸들러
     끝났네" 하고 연결을 닫음 → registry의 ws가 죽음. 그래서 안 끝나고 대기해야 함.
  2. **끊김 감지기.** 유저가 브라우저 닫으면 `receive_text`가 `WebSocketDisconnect`를
     던짐 → 잡아서 registry에서 remove. receive 안 하면 끊김을 못 알아 죽은 ws가 영영
     남음.

## 8. `while True`가 CPU를 안 태우는 이유 — busy-wait vs sleep-wait ★★

- `while True: pass`는 CPU 100% 태움(busy-wait). 근데 리더/핸들러의 while은 다름.
- `await ws.receive_text()` / `await r.xread(block=1000)`의 **`await`이 "이벤트 올
  때까지 자기"**를 함. CPU를 붙잡고 도는 게 아니라 이벤트 루프에 "메시지 오면 깨워줘"
  하고 비켜줌. 그동안 CPU는 다른 태스크 처리. → busy-wait이 아니라 **sleep-wait.**
- 그래서 sleep을 따로 안 넣음. 넣으면 "채팅 왔는데 sleep 때문에 늦게 처리"하는 손해만.
  이벤트 기반에선 sleep이 아니라 await으로 기다리는 게 정석.
- **`block=1000`도 sleep 역할 겸함:** stream에 채팅 있으면 즉시 반환, 없으면 최대 1초
  자고 확인. block 없이 xread하면 "없으면 즉시 빈 응답" → while 폭주 → busy-wait.

### block을 늘리면? — 얻는 것 없고 잃는 것 있음
- "일감 없을 때만 block되니 늘려도 성능 무관"은 **절반만 맞음.** 성능은 그대로지만
  **종료 반응성이 나빠짐.** `task.cancel()`은 태스크가 await 지점에 도달해야 실제
  취소됨. block=30000이면 최악 30초 자는 중이라 cancel 반응이 최대 30초 지연.
  block=1000은 최악 1초. 측정 런을 여러 번 돌리는 워크플로에선 이게 거슬림.
- 교훈: "바꿔도 되나?"를 물을 때 **얻는 것과 잃는 것을 양쪽 다** 따진다. block=1000이
  균형점(CPU 안 태움 + 종료 빠름 + 반응 촘촘).

## 9. 이벤트 기반 구조가 낯선 이유 ★

- 지금까지 짠 대부분은 **요청-응답**(요청 오면 처리, 값 return하고 끝). 익숙함.
- 리디자인은 **아무도 return을 안 함.** 리더는 무한루프로 남의 소켓에 밀어넣고, 핸들러는
  등록만 하고 대기, 데이터는 return이 아니라 registry(공유 변수)로 옆으로 흐름.
- 이걸 **이벤트 기반 / 발행-구독 구조**라 함. "질문하면 답한다"(요청-응답)가 아니라
  "방송국이 계속 틀고 채널 맞춘 사람이 받는다". 채팅·알림·실시간은 다 이 모양.
- design.md 학습목표 4번("비동기 큐·이벤트 아키텍처")이 이 낯섦을 통과하는 것.

### "live가 send를 안 하는 게 찜찜하다"는 감각 — 편견 아님
- 위화감의 정체: 이름이 live(중계)인데 send를 안 하고 등록만. 근데 live의 **책임은
  "이 유저를 이 방송 구독자로 연결"**이고, send는 그 책임의 수단일 뿐. 넷플릭스 재생
  버튼이 프레임을 직접 안 그리는 것과 같음(등록이 곧 재생 시작).
- 이 미감은 사실 **개인 큐 방식을 가리킴** — 개인 큐면 실제 send를 각 핸들러가 자기 큐
  비우며 하므로 send가 live로 돌아옴. 순서상 지금은 아님(6장 참고).

## 10. 개인 큐(버퍼) 방식 — 왜 지금은 아닌가 ★

- **네가 원래 떠올린 모델:** 리더는 버퍼에 넣기만, 핸들러가 꺼내서 자기 유저에 send
  (프로듀서-컨슈머). 틀린 게 아니라 **한 단계 더 나아간 버전.**
- **큐 하나면 안 됨:** 유저 800명이 컨슈머면 채팅 하나를 큐에 넣어도 **딱 한 명만**
  꺼내감(큐는 하나 넣으면 하나 나감). 팬아웃 안 됨. → **유저마다 개인 큐**를 둬야 함.
- 그러면 결국 `dict[bid, 유저별 큐 목록]`이 등장 → 방식 B의 레지스트리와 **같은
  자료구조** + "개인 큐 + 그 큐 비우는 태스크"를 한 겹 더 얹은 것.
- **개인 큐의 진짜 값어치 = 느린 유저 격리.** 리더가 `await ws.send_text`를 직접 하면,
  느린 유저 하나에서 막혀 뒤 799명이 다 밀림. 개인 큐면 리더는 `put_nowait`으로 던지고
  지나가니 느린 유저는 자기 큐만 쌓임(roadmap 1.3 "봇 호출이 중계를 막으면 안 된다"와
  같은 구조).
- **단, 팬아웃 선형성 자체는 안 사라짐:** 유저 수만큼 큐에 넣는 건 못 피함. `put_nowait`이
  `await send`보다 쌀 뿐 → 기울기만 완만, 선형이 상수가 되진 않음.
- **왜 지금 안 하나:** 1차 목표(연결 병목 제거)는 방식 B든 개인 큐든 똑같이 해결됨(둘 다
  리더 1개). 느린 유저 문제는 관측된 적 없는 2차 관심사. roadmap 정신("불편이 실제로
  터질 때 조각을 붙인다")대로 방식 B로 먼저 가고, 재측정에서 순차 send 병목이 실제로
  보이면 그때 개인 큐 + 전후 비교. 지금 방식 B 측정이 그 비교의 기준선.

## 11. 워커 수와 프로세스 세기 — 숫자의 세 층위 ★

- **`--workers 8` = FastAPI 앱을 8벌 복제한 8개 프로세스.** 각 워커는 "lifespan만 도는
  놈"이 아니라 **완전한 앱 하나** — 자기 lifespan(→reader), DB 풀, registry를 각자 갖고,
  `/chats`·`/stats`·`/live` 요청도 다 처리. reader가 워커를 독점하는 게 아니라 워커 안
  백그라운드 태스크로 돌 뿐(asyncio라 reader가 await로 자는 동안 요청 처리).
- **그래서 워커마다 registry가 따로.** 유저는 uvicorn이 분산해준 한 워커에 붙고, 그
  워커의 reader가 걔한테 뿌림. 채팅 하나를 8개 워커의 reader가 각자 읽음(워커당 1회
  읽기는 남음) → `blocked_clients = 워커 수 = 8`.

### 프로세스 세기 함정
- `ps aux | grep uvicorn` → **마스터만** 보임. 워커는 프로세스명이 `python`이라 안 걸림.
- `pgrep -P <마스터PID>` → 자식 9개. **워커 8 + resource_tracker 1.**
  - macOS는 spawn 방식 → 워커가 `python -c "from multiprocessing.spawn import spawn_main"`.
  - 트래커는 `python -c "from multiprocessing.resource_tracker import main"`. 앱 안 돌림.
- **세 층위 정합:** 마스터 1 / 자식 9(워커8+트래커1) / blocked 8(reader 돌리는 워커만).
  트래커는 reader 없어 blocked에 안 잡힘. → 자식 9인데 blocked 8.
- **교훈: 워커 수는 프로세스 목록보다 `blocked_clients`가 더 믿을 지표.** 프로세스엔
  트래커 같은 앱 안 돌리는 것이 섞이지만, blocked엔 실제 Redis 연결한 reader만 잡힘.

### 진짜 reader 1개로 만들려면
- 워커를 1개로 줄이거나(`--workers 1`), reader를 별도 프로세스로 빼고 **pub/sub으로 각
  워커에 전파**. 후자는 "별도 프로세스 reader가 워커별 registry를 못 봐서"(프로세스가
  달라) 필요. 08/현재는 8개로 충분(과함 회피).

## 12. 시각 넘기기 재확인 — time.time() (10장 반복) ★

- k6 지연 = (k6 도착시각 `Date.now()/1000`) − (주입 발생시각 `time.time()`). 두 시각이
  **다른 프로세스**에서 찍힘 → `time.time()`(벽시계)이라야 프로세스 건너 유효.
  `perf_counter`(임의 0점)는 불가.
- **단위 통일 필수:** `Date.now()`는 ms → `/1000`으로 초 맞춤. `sent`(파이썬 초)와 통일
  안 하면 1000배 틀림. `delay.add((now - sent) * 1000)`으로 다시 ms 변환해 기록.
- **같은 머신이라 두 벽시계가 일치**해서 이 뺄셈이 유효. k6를 별도 머신으로 빼면 두
  기계 시계 오차(NTP)가 지연에 섞임 → 그때 시계 동기화가 새 변수.

### chat_delay는 "채팅별 첫↔막 유저 차이"를 직접 못 잰다
- 각 지연값은 (그 유저 도착 − 발생)이라 기준이 발생시각 하나. "첫 유저 대비 내가 얼마나
  늦었나"가 아님. k6의 각 vu는 서로를 몰라 같은 채팅끼리 짝지을 창구도 없음.
- **하지만 p95·p99(꼬리)가 그걸 간접적으로 담음.** 리더가 순차 send → 마지막 유저가 앞
  전원을 기다려 지연 큼 → 그 큰 값이 p99로 감. 구독자 수 올릴 때 p99가 어디서 꺾이나가
  팬아웃 한계. 채팅별 첫↔막을 직접 안 재도 관측됨(직접 측정은 무거워서 지금은 안 함).

## 13. 측정 도구 자신이 병목이 되는 순간 ★★ (이번의 큰 교훈)

- k6가 같은 맥북에서 돎 → k6 CPU만큼 서버가 손해(08 7장 반복). 800에선 10~16%로
  가벼웠지만, **2000+에선 k6가 300~400%(코어 3~4개)로 서버(~110%)보다 먼저 병목.**
- **파이썬 워커는 GIL로 개별 ~100%가 상한** → 하나가 313%를 못 먹음 → 400%는 멀티스레드
  k6(Go) 확정. top의 %CPU는 코어 하나=100% 기준(10코어면 이론상 1000%).
- **코어가 많아도 소용없음:** k6와 서버가 같은 코어를 나눠 쓰는 한 순수 서버 한계 안 나옴.
  k6를 별도 머신으로 빼야 서버가 코어 독점 → 진짜 한계 측정. 단 서버 외부 노출 →
  네트워크 지연이 새 변수(측정 성격 변화).
- **판정법:** top으로 워커 CPU 합과 k6 CPU를 **따로** 본다. 어느 쪽이 먼저 100%(코어
  포화)에 닿나가 병목. 이번엔 k6가 먼저 → "서버 한계 미측정, 도구 병목 규명"이 결론.
- **오염값 식별:** vus 2000 고정 p95(55ms)가 ramp 2224(27ms)보다 나쁨(모순) +
  `ws_connecting` max 4초 + `vus min 66` = k6가 못 버틴 흔적. **재현 안 되면 환경 요인**
  (08 원칙) → 이 값은 서버 성능으로 안 씀.

## 14. 이번 세션 성과 (한 줄)

08이 찾은 "구독자당 Redis 연결" 병목을 **리더 1개 + 레지스트리 + 앱 내부 배분**으로
고쳐 `blocked_clients`를 구독자 수 → 워커 수(8)로 분리했다. 재측정에서 서버는 2000명에도
여유(워커 CPU ~110%)였고, 이번엔 **측정 도구(k6)가 먼저 병목**임을 CPU로 규명 —
"한계를 못 잰 게 아니라 왜 이 환경에서 못 재는지를 밝힌" 것이 수확. 요청-응답에서
이벤트 기반 구조로 넘어온 세션.
