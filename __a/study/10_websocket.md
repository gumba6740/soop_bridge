## 1. WebSocket 부하는 REST 부하와 성격이 다르다 ★

- **REST 요청** = 짧게 두드리고 떨어짐. 요청 하나가 완결되고 유저는 wait_time 쉬고
  또 요청. 특정 순간 열린 요청은 유저 수보다 적음. 지표 = **RPS(처리량)**.
- **WebSocket** = 연결을 열고 **계속 붙잡음**(`while True`로 채팅 올 때까지 대기).
  끊지 않음. 지표 = **동시 연결 수**.
- 그래서 부하의 질문이 다름:
  - REST: "초당 몇 번 두드리나(RPS 천장)"
  - WS: "동시에 몇 개를 붙잡고 있나 + 그때 중계가 밀리나·메모리 추이"

### 왜 Locust가 아니라 k6인가
- Locust 유저 모델 = "task 하나 하고 → 쉬고 → 또" 순환. "연결 열고 무한정 붙잡기"를
  자연스럽게 표현 못 함. 억지로 물리면 통계(RPS)가 의미 없어짐.
- k6 = Go 기반, 수천 동시 연결에 강함. WebSocket에 적합.
- k6는 WebSocket 전용 아님(HTTP도 됨). 그냥 이 용도에 Locust보다 나아서 선택.
- k6는 파이썬 패키지 아님 → `uv add` ✗, `brew install k6` ○. 시나리오는 JS로
  작성하되 브라우저/Node가 아닌 **k6 전용 런타임**(`import ws from 'k6/ws'`,
  `k6 run script.js`).

## 2. k6 기본 ★

### 구조
```javascript
import ws from 'k6/ws';
import { Trend } from 'k6/metrics';

const delay = new Trend('chat_delay_ms');   // 커스텀 지표

export const options = { vus: 100, duration: '30s' };  // 약속된 이름

export default function () {                 // 약속된 진입점(유저 1명의 시나리오)
  ws.connect(url, {}, function (socket) {    // 연결되면 실행될 콜백
    socket.on('message', function (msg) {    // 메시지 오면 실행될 콜백
      delay.add(계산한_지연);
    });
    socket.setTimeout(() => socket.close(), 30000);
  });
}
```

- **`export const options`** / **`export default function`** = k6가 인식하는 **약속된
  이름/진입점**. options는 설정(vus/duration), default function은 유저마다 반복 실행.
- **vus**(virtual users) = 동시 유저(구독자) 수. **이 실험의 독립변수.** 명령줄로도:
  `k6 run --vus 500 --duration 30s script.js` (파일 options보다 우선).
- **`Trend`**(대문자=클래스) = 커스텀 지표 기록기. `new Trend('이름')`으로 만들고
  `.add(값)`으로 관측값을 **쌓음**(append 계열, 덧셈 아님). 런 끝나면 k6가 그 값들의
  avg/p95/p99를 자동 계산.
- **콜백 패턴** = "이 일 생기면(연결됨/메시지옴) → 이거 해라"를 함수로 등록.
  `function`은 **정의**(파이썬 `def`), 지금 실행 아님. 실제 실행은 이벤트 때 k6가
  대신 호출. 정의(만들어 넘기기)와 호출(때가 되면 실행)이 분리됨.

### k6 리포트 읽는 법
- **`chat_delay_ms`**(내 커스텀) = 채팅 발생→도착 지연. 밀림의 직접 지표.
- **`ws_connecting`** = 연결 **수립**에 걸린 시간(30s 붙어있는 것과 무관). 정상 몇 ms,
  폭주하면 초 단위 → **연결 수락 병목** 신호.
- **`ws_msgs_received`/s** = 받은 메시지 초당 수. 팬아웃이라 주입(10/s)보다 훨씬 큼
  (구독자 수 배). 이게 정체되면 서버가 못 뿌리는 것.
- **`iterations`** = default function이 처음~끝 한 바퀴 돈 횟수. 정상이면 vus와 비슷.
  **부풀면(vus보다 훨씬 큼) = 유저가 죽고 재생성 반복**(연결 실패).
- **`iteration_duration` / `ws_session_duration`** = 유저 하나가 산 시간. 30s여야
  정상. 짧으면(2ms 등) 일찍 죽음.
- **`vus min`** = 실행 중 활성 유저 최저치. 목표(max)보다 낮으면 유지 실패.
- **진단 우선순위:** 숫자 해석 전에 "제대로 이어졌나" 먼저 — `ws_msgs_received`가
  0이면 아무것도 못 받은 것(서버/주입/bid 확인), 지연이 음수·수천ms면 시계/단위 오류.

## 3. 시각을 프로세스 건너 넘기기 — time.time() vs perf_counter ★

- 중계 지연 = (도착 시각, k6) − (발생 시각, 주입 파이썬). **두 시각이 다른
  프로세스에서 찍힘** → 발생 시각을 메시지에 실어 보내야 함.
- **`perf_counter`는 못 씀.** 임의의 0점에서 흐른 초(기준점 undefined). **같은
  프로세스 안 두 시점 차이**에만 유효. 프로세스마다 0점이 달라 넘기면 쓰레기값.
  (단조 증가·고정밀이라 한 프로세스 구간 측정엔 최적 — make_dummy가 이걸 쓴 이유.)
- **`time.time()`을 씀.** 1970 기준 절대 시각(벽시계). 모두가 같은 기준을 봐서
  프로세스·기계 건너 빼도 유효. 단 **단조 아님** — NTP/시계조정으로 뒤로 갈 수
  있음(구간 측정엔 위험). "넘기기"가 필수라 단조성을 포기하고 씀.
- **판단 기준:** 두 시점을 내가 다 재나 → perf_counter. 시각을 남에게 넘기나 →
  time.time(). "절대 시각이면서 단조인 시계"는 존재하지 않음(택1).
- **형식은 숫자(Unix timestamp)로.** isoformat 문자열은 k6의 `Date`가 ms로 뭉개고
  파싱 번거로움. `parseFloat` 한 방 되는 숫자가 정석. 표시용≠계산용.
- `time.time()`과 `datetime`은 별개 모듈(이름만 비슷). `datetime.now(UTC).timestamp()`
  == `time.time()`(둘 다 Unix 초). 이미 datetime import했으면 후자로 import 절약.

### 실서비스 코드 안 건드리는 우회
- `stream_chats`가 구독자에게 message/uid/unick만 보냄(received_at 버림). 발생 시각을
  정식 필드에 넣으면 전달 안 됨.
- → **`parts[0]`(message 자리)에 타임스탬프를 위장해 넣음.** 이미 message는 전달되니
  코드 수정 0. k6가 `msg.split(': ')[1]`로 뒷부분(타임스탬프) 떼서 계산.
- 원칙: 재는 대상(stream_chats) 코드를 건드리면 그게 변수가 됨. 우회로 조건 통제.

## 4. Redis 연결 — 서버 상한 vs 클라이언트 풀 상한 ★★

이 세션 최대 발견. **"Redis 풀 무제한" 이전 지식이 틀렸음.**

### 두 개의 다른 상한
- **Redis 서버 `maxclients`** (INFO clients에서 10000) = 서버(건물)가 받는 총 연결.
  DB 번호(0~15) 16개랑 **무관** — 나누는 것 아님, 서버 전체 총합이 1만.
- **클라이언트 풀 `max_connections`** = 내 앱이 `from_url`로 만든 풀이 만드는 연결
  상한. **내 코드가 정함**, 서버가 아님. redis-py 기본값이 있음(무제한 아님!).
- **병목은 후자였다.** 800 구독자에서 `MaxConnectionsError`는 redis-py(클라이언트)
  코드에서 남 → 서버(1만)가 아니라 **앱 풀**이 막음. 서버는 800쯤 우습게 받는데
  내 앱이 자기 풀 상한(500~800)에서 먼저 끊음.

### 싱글턴 ≠ 연결 개수
- `app.state.redis` 클라이언트 **객체**는 1개(싱글턴). 하지만 그 객체가 내부에
  **연결 풀**을 갖고, 풀이 **여러 연결**을 만듦. 객체 하나여도 연결 500개 가능.
- 800에서 터진 건 "싱글턴이라서"가 아니라 **풀의 max_connections 상한** 때문.
- 풀 상한만 키우면(`max_connections=10000`) 싱글턴 객체 하나로도 1만까지 가능.
  근데 그건 나쁜 해법(아래).

### blocked_clients = 구독자 수 (구조 확정)
```
connected_clients: 502
blocked_clients:   500   ← 구독자 500명과 1:1
maxclients:        10000
```
- `stream_chats`가 구독자마다 `xread(block=1000)` → 각자 연결 1개를 **blocking**으로
  점유(응답 올 때까지 반납 안 함) → blocked 500.
- **구독자 수 = Redis 연결 수**라는 선형 구조가 숫자로 드러남. 이게 확장을 막는
  근본 원인.

### 왜 풀 키우기가 나쁜 해법인가
- 풀을 1만으로 키우면 서버 상한(1만)까진 감. 근데 **blocked 연결 1만 개** = 같은
  stream을 1만 번 각자 읽는 낭비. 채팅 하나에 Redis가 1만 blocked를 다 깨움.
- 한계를 **뒤로 밀 뿐** 없애지 못함. "구독자당 연결 1개" 구조가 그대로.

## 5. 해결 구조 — "하나가 읽어 여럿에 뿌리기" ★

- **문제의 정확한 정체:** "읽기 루프가 상시 도는 것"이 아니라 **"요청마다 읽기 루프가
  생기는 것"**. 상시 도는 것 자체는 괜찮음. 요청과 무관하게 앱당 하나면 됨.
- **읽는 놈을 하나만:** `lifespan`에서 `asyncio.create_task`로 백그라운드 읽기 태스크
  1개. 요청과 무관하게 앱 수명 동안 stream tail. **Redis 연결 1개**(구독자 수 무관).
- **구독자 레지스트리:** bid별 WebSocket 목록을 앱 메모리에 보관.
- **핸들러는 등록만:** 접속 시 레지스트리 add, 끊기면 remove. Redis 직접 안 읽음.
- 읽기 태스크가 채팅 읽으면 → 해당 bid 구독자 전원에게 **앱 내부에서** 배분(Redis
  재접근 없음).
- 효과: `blocked_clients`가 구독자 수와 무관하게 **항상 1**. 풀·서버 상한 안 건드림.
  같은 stream 중복 읽기(800배)도 사라짐.

### 비유
- 지금 = 800명이 각자 우체국(Redis) 가서 "내 편지 왔어?" → 마비.
- 바꿈 = 우체부 1명이 우체국에서 받아와 800집에 배달 → 우체국은 1명만 상대.

## 6. 아키텍처 판단 — 무엇을 분리하고 무엇을 붙이나 ★

- 원래 프로듀서/컨슈머/FastAPI 분리 이유 = 독립적으로 죽고 살고, 독립 확장.
- **핵심 질문: "무엇이 무엇과 생명주기를 공유해야 하나"를 기능별로 나눈다.**
  "다 분리가 좋다"가 아니라, 분리가 이득인 것과 붙는 게 이득인 걸 구분.
- **데이터 파이프라인(수집·저장·분석)** = uvicorn과 **독립** 프로세스 유지. 중계
  안 해도 채팅은 계속 수집·저장돼야 함. 서버 생명주기와 무관.
- **실시간 중계** = FastAPI **내장**(백그라운드 태스크). 구독자 WebSocket이 FastAPI에
  붙으므로, 뿌리는 것도 거기서 해야 닿음. **프로듀서에 못 붙임**(프로듀서엔 구독자
  WebSocket이 없음).
- 같은 "stream 읽기"라도 목적(저장 vs 중계)·생명주기가 달라 **읽는 주체를 둘로**:
  컨슈머(xreadgroup, ack하며 소비, 저장) / 중계 리더(xread tail, 뿌리기).

### 워커 수 함정
- `--workers 8`이면 lifespan이 워커마다 실행 → 읽기 태스크 8개(연결 8개). 800→8은
  100배 개선이나 완전한 1개는 아님. 진짜 1개는 별도 단일 리더 + pub/sub 전파 등
  추가 구조 필요. 1차 목표는 8개로 충분.

### pub/sub 대안
- stream+xread 대신 Redis pub/sub도 가능(채널 구독 시 Redis가 알아서 뿌림). 단
  pub/sub 구독도 연결을 잡으므로 "하나가 구독해 앱 내부 배분"이라는 핵심 구조는
  동일하게 필요. 읽기 방식의 차이일 뿐.

## 7. 측정 도구·환경 함정 (T4-1 교훈의 반복·심화)

- **측정 도구 자신의 리소스:** k6도 같은 맥북에서 돎 → k6가 먹는 CPU만큼 서버가
  손해. vus 500서 k6 CPU 10~16%(가벼움, Go 이점). 하지만 실전엔 k6 없으니 순수
  서버는 더 여유. 측정 시 "이만큼은 도구 몫" 감안. 완전 제거하려면 k6를 별도 머신에서.
- **`top`은 시스템 전체 뷰어**(uvicorn 전용 아님). uvicorn 꺼져도 작동, 목록에 안 뜰
  뿐. uvicorn은 프로세스명이 **`python`**으로 떠서 "uvicorn"으로 못 찾음 →
  `pgrep -f uvicorn`(명령줄 전체 검색)으로 필터.
- **WindowServer CPU** = `top` 화면 실시간 갱신의 부산물. 실전(headless)엔 없음.
  측정 환경 노이즈로 감안.
- **소켓 노이즈:** WebSocket은 연결을 오래 잡아 소켓 자원(TIME_WAIT) 포화가 REST보다
  쉬움. 같은 vus인데 런마다 `ws_connecting` 출렁(500의 2초 튐이 이것). **런 사이
  텀** 주고, **재현되는 값만 신뢰**(chat_delay는 재현됨→신뢰, ws_connecting은
  범위로만). 08 노트의 "재현 안 되면 환경 요인" 원칙 반복.

### 셸/도구 부품 메모
- **`pgrep -f 패턴`** = 프로세스에서 패턴 찾아 PID 반환("process grep"). `-f`=명령줄
  전체 검색. 여러 개는 `"uvicorn|k6"`(정규식 OR, 따옴표 필수).
- **`tr 'A' 'B'`** = 문자 1:1 치환(줄바꿈→쉼표). **`sed 's/,$//'`** = 패턴 치환,
  `,$`는 끝 쉼표, 빈 치환=삭제. (pgrep 줄바꿈 출력을 top -pid의 쉼표 형식으로 성형)
- **`top -o cpu`** = CPU 순 정렬(`-o`=order). 전체 중 화면 크기만큼 표시되니 정렬해야
  uvicorn/k6가 위로. **`top -l 1`** = 1회 스냅샷(실시간 갱신 없이 한 장, 요동 없어
  읽기·복사 편함). `-s N`=갱신 간격.

### JS 문법 메모 (파이썬과 차이)
- `const`=재할당 불가 변수, `let`=가변. 파이썬은 그냥 `x=`지만 JS는 선언 키워드 필요.
- `new Trend()`=객체 생성(파이썬은 `Trend()`, JS는 `new` 명시).
- 클래스는 대문자 관습(Trend).
- **JS는 키워드 인자 없음** — 위치로만 전달. 중간 인자 건너뛰기 불가 → 뒤 인자 주려면
  앞자리를 빈 값(`{}`, `null`)으로 메움. `ws.connect(url, {}, cb)`의 `{}`가 그 이유
  (파이썬이면 `connect(url, callback=cb)`로 우아하게 건너뜀).
- `{}` = 빈 객체 = 파이썬 빈 dict.

## 8. 이번 실험 성과 (한 줄)

"동시 구독자 한계 측정"이 **"구독자당 Redis 연결 구조가 확장을 막는다"는 아키텍처
결함 발견**으로 이어짐. 숫자가 이상한 걸(800<500) 노이즈로 안 넘기고 파고들어
`MaxConnectionsError`를 찾은 게 핵심. 실서비스 전에 찾은 게 다행. 팬아웃/CPU 한계는
리디자인 후 재측정 대상.
