# 비공개 API 리버스 엔지니어링 — 개념 정리

## 배경

공식 문서가 없는 비공개 API의 엔드포인트(URL, 파라미터 등)를 찾아내는 과정을 **API 리버스 엔지니어링**이라고 한다. SOOP(구 아프리카TV)의 VOD API를 사례로, 어떤 방법들이 있고 각각의 원리가 무엇인지 정리한다.

---

## 1. 브라우저 개발자 도구 (F12 Network 탭)

가장 기본적인 방법. 브라우저가 서버에 보내는 HTTP 요청을 실시간으로 볼 수 있다.

- **XHR/Fetch 필터**를 걸면 API 호출만 걸러서 볼 수 있다.
- 요청 URL, 메서드(GET/POST), 헤더, 파라미터, 응답 JSON을 전부 확인 가능.

**한계:** SSR(서버 사이드 렌더링)을 쓰는 사이트에서는 API 호출이 서버에서 이루어지기 때문에 브라우저 Network 탭에 잡히지 않는다. 예를 들어 Next.js 기반 사이트는 서버가 API를 호출한 뒤 결과를 HTML로 만들어서 브라우저에 내려주므로, 브라우저 입장에서는 API 호출이 없는 것처럼 보인다.

---

## 2. 프록시 (Proxy)

### 프록시란?

클라이언트(폰, 브라우저)와 서버 사이에서 **요청을 대신 전달해주는 중간 서버**다.

```
일반 통신:    폰 → 서버
프록시 사용:  폰 → 프록시(PC) → 서버
```

프록시는 요청을 받아서 서버에 그대로 전달하고, 서버의 응답도 그대로 폰에 돌려준다. 헤더, 바디 등 모든 내용을 그대로 넘긴다.

### mitmproxy

**Man-In-The-Middle Proxy**의 약자. 중간에서 트래픽을 가로채서 **내용을 읽을 수 있게** 해주는 디버깅 도구다.

사용 흐름:

1. PC에서 mitmproxy 실행 → PC가 8080 포트에서 대기하는 프록시 서버가 됨
2. 폰의 Wi-Fi 프록시 설정에 PC의 IP와 포트(8080)를 입력
3. 폰의 모든 트래픽이 PC를 경유하게 되어, mitmproxy 화면에서 요청/응답을 볼 수 있음

### HTTPS와 CA 인증서

HTTPS 통신은 암호화되어 있어서, 프록시가 중간에 있어도 내용을 읽을 수 없다. mitmproxy가 HTTPS 내용을 보려면 다음과 같은 과정이 필요하다:

```
원래:  폰 ←── 암호화 ──→ 서버

mitmproxy 끼우면:
       폰 ←── 암호화1 ──→ mitmproxy ←── 암호화2 ──→ 서버
```

mitmproxy는 서버인 척 **가짜 인증서**를 폰에 제시한다. 폰이 이 인증서를 신뢰해야 암호화1 구간이 성립하고, mitmproxy가 내용을 복호화해서 읽을 수 있다.

이때 필요한 것이 **CA 인증서(Certificate Authority)**다.

- **CA**는 "이 인증서는 진짜다"라고 보증해주는 인증 기관이다.
- mitmproxy의 CA 인증서를 폰에 설치하면, 폰이 "mitmproxy가 발급한 인증서도 신뢰한다"고 인식한다.
- 이를 통해 mitmproxy가 만든 가짜 인증서를 폰이 받아들이게 되어, HTTPS 트래픽도 복호화해서 볼 수 있다.

### SSL 피닝 (Certificate Pinning)

일부 앱은 OS의 인증서 저장소를 무시하고, **앱 코드 안에 신뢰할 인증서를 직접 박아놓는다.** 이것이 SSL 피닝이다.

- OS: "CA 인증서가 설치되어 있으니 통과" ✅
- 앱: "내가 아는 인증서가 아니니 거부" ❌

이 경우 폰 → 프록시 구간에서 연결 자체가 성립하지 않는다. 프록시가 서버에 요청을 보낼 기회조차 없다. SOOP 앱이 이 방식으로 mitmproxy를 차단했다.

### 리버스 프록시 vs 포워드 프록시

- **포워드 프록시** (mitmproxy): 클라이언트 쪽에서 요청을 대신 전달. 디버깅이나 트래픽 분석 용도.
- **리버스 프록시** (nginx, Caddy): 서버 앞에서 요청을 받아 분배. 서버 배포에서 사용. 별개의 개념이다.

## 3. APK 디컴파일

### APK란?

**Android Package**. 안드로이드 앱의 설치 파일이다. 코드, 이미지, 설정 파일 등 앱에 필요한 모든 것이 압축되어 들어있다. Play 스토어에서 앱을 다운받을 때도 내부적으로는 APK를 받아서 설치하는 것이다.

### APK 구하기

APKMirror 같은 사이트에서 다운받을 수 있다. 이 사이트는 Play 스토어에 올라온 앱의 APK를 수집해서 공개적으로 배포한다. 사용자가 폰에서 추출한 APK를 업로드하면, 사이트가 Play 스토어 원본과 서명을 비교해서 검증 후 공개한다.

### jadx

APK를 **사람이 읽을 수 있는 Java 소스코드로 복원**해주는 디컴파일 도구다.

```
개발자: Java/Kotlin 소스코드 → 컴파일 → APK(바이너리)
jadx:   APK(바이너리) → 디컴파일 → Java 소스코드(복원)
```

원래 언어가 Java든 Kotlin이든 상관없다. 안드로이드 앱은 모두 DEX(Dalvik Executable) 형태로 컴파일되고, jadx는 DEX를 읽기 때문이다.

### 난독화 (Obfuscation)

앱 배포 시 코드 분석을 어렵게 만들기 위해 적용하는 기법이다.

- 클래스명, 메서드명, 변수명이 `bi0`, `v46`, `dn7` 같은 의미 없는 이름으로 바뀐다.
- 패키지 구조도 깨져서 `defpackage`에 몰린다.
- 다만 **문자열은 바꿀 수 없다.** API URL(`https://api.m.sooplive.com`), 파라미터명(`nTitleNo`), 에러 메시지 등은 서버가 알아들어야 하므로 그대로 남는다.

따라서 jadx로 디컴파일한 뒤 **문자열 검색**으로 API 엔드포인트를 찾을 수 있다.

### 보안 한계

APK를 누구나 디컴파일할 수 있으므로, 앱의 API 구조, 비즈니스 로직, 하드코딩된 키 등이 노출될 수 있다. 이를 막기 위한 방어 수단:

- **SSL 피닝** — 트래픽 가로채기 방지
- **난독화** — 코드 분석 난이도를 높임
- **서버 인증** — 중요 로직은 서버에서 처리
- **앱 무결성 검증** — 변조 여부를 서버가 체크

하지만 앱이 서버에 요청을 보내려면 URL과 파라미터를 반드시 알아야 하므로, 충분히 파면 찾을 수 있다. 완벽하게 숨기는 것은 불가능하고, **찾기 어렵게** 만드는 것이 목적이다.

## 4. API 리버스 엔지니어링 방법 요약

| 방법 | 도구 | 원리 | 한계 |
|------|------|------|------|
| Network 탭 | 브라우저 F12 | 브라우저의 HTTP 요청을 관찰 | SSR이면 API 호출이 안 보임 |
| JS 소스 분석 | 브라우저 Sources 탭 | JS 번들 안의 API 경로 문자열 검색 | 번들이 크면 찾기 어려움 |
| 프록시 트래픽 분석 | mitmproxy, Charles | 폰/브라우저 트래픽을 PC에서 가로채서 관찰 | SSL 피닝 시 차단됨 |
| APK 디컴파일 | jadx | 앱 소스코드에서 API URL 직접 검색 | 난독화로 코드 흐름 파악이 어려움 |
| GitHub 검색 | - | 다른 사람이 정리해둔 비공식 문서 참고 | 최신 정보가 아닐 수 있음 |
| SSL 피닝 우회 | Frida | 앱의 인증서 검증 로직을 우회 | 루팅 필요, 세팅이 복잡 |

## 5. 기타 개념

### HTTP 응답과 JSON 파싱

HTTP 통신은 텍스트 기반이다. 서버가 dict 같은 데이터 구조를 보낼 때는 JSON 문자열로 직렬화해서 전송하고, 클라이언트가 이를 다시 파싱해서 dict로 복원한다.

```
서버:       dict → json.dumps() → 문자열 → 네트워크 전송
클라이언트:  문자열 수신 → resp.json() → dict 복원
```

### SSR (서버 사이드 렌더링)

서버에서 API를 호출하고, 그 결과를 HTML로 만들어서 브라우저에 내려주는 방식. 브라우저는 완성된 HTML을 받기만 하므로, 브라우저 입장에서는 API 호출을 관찰할 수 없다. Next.js 같은 프레임워크가 대표적이다.

### 공식 API vs 비공식 API

- **공식 API:** 서비스 제공자가 문서를 공개하고, API 키 발급 등 절차를 통해 사용을 허가. 안정적이지만 접근에 제약이 있을 수 있다.
- **비공식 API:** 앱이나 웹이 내부적으로 사용하는 API를 리버스 엔지니어링으로 찾아낸 것. 공식 문서가 없고, 서비스 제공자가 언제든 변경하거나 차단할 수 있다.
