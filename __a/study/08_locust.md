## 1. Locust — 부하 도구 첫 사용

- **정체:** 파이썬 라이브러리 + 웹 GUI 한 몸. `pip/uv add locust`.
  파이썬 파일(`locustfile.py`)에 "가상 유저 한 명의 행동"을 `@task`로 적으면,
  Locust가 그 유저를 수백~수천 명 복제해 동시에 서버를 두드리고 통계를 낸다.
- **딸려온 의존성(flask 등)은 지우지 말 것.** flask는 Locust의 웹 대시보드
  (`:8089`)를 만드는 부품. gevent/greenlet은 가상 유저 동시성 엔진. 전부
  Locust의 몸통. `uv remove locust` 하면 알아서 정리됨.
- **실행:** 서버 먼저(`--reload` 없이) → `locust -f locustfile.py --host ...`
  → 브라우저 `:8089`(터미널에서 Enter로도 열림)에서 유저수·spawn rate 넣고 Start.
- **종료:** 브라우저 Stop = 부하만 멈춤(재시작 가능). 터미널 `Ctrl+C` = 완전
  종료 + 최종 요약 표 출력.
- **결과 파일:** 분석용은 **requests CSV**가 제일 깔끔(즉시 파싱). 단 CSV엔
  유저 수·에러 종류가 없음 → 그건 HTML 리포트(`window.templateArgs` JSON)에 있음.
  조건은 파일명/메모로 같이 남긴다.

### ramp up / spawn rate
- **ramp up** = 유저를 한 번에 안 넣고 정해진 속도로 늘리는 것. 그 속도가
  **spawn rate**(초당 몇 명씩).
- 왜 천천히? ① 현실(시청자가 점점 몰림) 재현 ② **"몇 명째부터 무너지나"**
  (임계점)를 관측하려고. 한 번에 쾅 넣으면 임계점이 안 보임.
- 급하게 올리면 "진짜 한계라 무너진 건지 급증 때문인지" 원인이 섞인다.

### 언제 멈추나
- 요청 수(#reqs)는 기준이 아님(오래 켜두면 계속 늚). 기준은 **"숫자가
  안정(stabilize)됐나"**. Charts 탭에서 응답시간 선이 **평평해지면** 그때 p95를 읽는다.

## 2. 서버 구조 — 프로세스 · 스레드 · async 3층

- **워커(`--workers N`) = 프로세스 N개.** 스레드 아님. 마스터 1 + 워커 N.
  각 워커는 독립 메모리, CPU 코어를 진짜 병렬로 씀(파이썬 GIL 우회 = 프로세스
  나누기).
- **async(event loop)** = 워커 하나가 스레드를 안 늘리고도 수백 연결을 저글링.
  `await`가 "기다리는 동안 딴 요청 처리해도 됨" 표시.
- 정리: **프로세스로 CPU를 넓히고, async로 각 프로세스 안 연결을 저글링.**
  스레드 층은 async 서버에선 거의 안 씀.
- **워커 상한 ≈ CPU 코어 수** (내 맥북 10코어). 코어보다 많이 띄우면 서로
  코어를 뺏어(context switch) 오히려 느려질 수 있음. 그리고 워커↑ = DB 풀도
  워커마다 생겨서 Postgres 커넥션이 폭증할 수 있음.

### async를 언제 쓰나 (더미 스크립트에서 배운 것)
- async 이득 = "기다리는 동안 다른 일 할 게 있을 때". **할 일이 하나뿐인
  스크립트(더미 100만 삽입)는 동기가 낫다.** COPY가 빠른 건 async 덕이 아니라
  COPY 자체가 빠른 것.

## 3. 병목은 하나가 아니라 "계단"이다 ★

부하를 올리며 병목을 하나씩 벗겨냄. **앞을 치우면 다음이 드러난다(양파 껍질).**

```
워커 1개  → 연결 못 받음(Connection reset)   [워커 4로]
워커 4개  → 1000유저서 연결 한계             [워커 8로]
워커 8개  → DB 커넥션 4개 대기(응답 지연)     [풀 max_size=10]
풀 10개   → 이제 쿼리 자체가 병목            [인덱스로]
```

### 신호 읽는 법
- **연결 거부(Connection reset / Remote disconnected)** = 앞단(워커/연결) 병목.
  "입장 자체를 못 함."
- **실패는 0인데 응답시간만 증가** = 뒷단(풀/쿼리) 병목. "입장은 했는데 안에서
  기다림."
- **응답시간 멀쩡한데 연결만 튕김** = 처리(DB) 문제 아님. 연결 앞단 문제.

### DB 커넥션 풀 (psycopg)
- `AsyncConnectionPool(url)`만 쓰면 `min_size=4`, `max_size=None`.
  **max_size None = min이 천장 = 고정 크기 4.** (공식 문서: no max_size 또는
  max_size=min_size면 고정 크기)
- `max_size=10`으로 주면 동적 크기: 평소 4개, 부하 오면 최대 10개까지 생성.
- 병목 원리: 유저 많은데 커넥션 적으면, 초과 요청이 "커넥션 빌 때까지" 대기 →
  그 대기가 응답시간에 더해짐. 은행 창구 4개에 손님 1000명.
- `PoolTimeout: couldn't get a connection after 30 sec` = 풀 고갈 + 느린 쿼리가
  커넥션을 오래 붙잡은 결과. (인덱스 없을 때 이게 터짐 → 인덱스 필요성의 증거)

### 처리량 포화(saturation)
- **RPS ≈ 유저수 ÷ (응답시간 + wait_time).** 응답이 느려지면 유저당 처리량이
  줄어 RPS가 천장을 침. 유저를 더 넣어도 RPS 정체 + 응답만 증가 = 포화 지점 =
  현재 처리량 한계.

### 측정 도구 자신의 한계 ★
- Locust도 파이썬 → 기본 코어 1개만 씀. 유저 2000쯤이면 **Locust가 먼저 지쳐**
  `CPU usage too high` 경고. **이 경고 뜬 런의 숫자는 못 믿는다**(서버가 아니라
  부하 생성기가 굼떠서 나온 가짜 지연). 해법: `--processes`로 Locust 분산.
- **"측정 대상의 문제냐, 측정 도구/환경의 문제냐"를 늘 가려야 한다.**

### 재현 안 되는 실패는 깊이 파지 않는다
- 같은 조건인데 됐다 안 됐다 → 원인이 "그 순간에만 있던 일시 상태"(TIME_WAIT
  소켓 포화 등). 코드 원인이면 반드시 재현됨. 재현 안 되면 환경 요인으로
  결론하고 넘어간다. **재현되는 것만 신뢰·기록.**

## 4. 인덱스 ★★

### 왜 필요한가 (근본)
- **테이블은 "삽입된 순서"로 저장된다. received_at 순서가 아니다.**
  실제 채팅은 시간순 삽입이라 우연히 일치할 뿐. 더미는 received_at을 랜덤으로
  넣어서 물리 순서와 어긋남 → 조회 시 전체 훑고 정렬해야 함.
- 인덱스 = "특정 컬럼 기준으로 미리 정렬해둔 별도 지도." 본체는 삽입순으로
  두고, 인덱스가 길잡이. **DB가 정렬 저장을 안 하기 때문에 인덱스가 존재.**
- 비유: 책이 들어온 순서로 꽂힌 책장(테이블) + 제목→위치 색인카드(인덱스).

### 복합 인덱스 (composite) — 따로 2개 ≠ 묶어서 1개
- `WHERE bid=? ORDER BY received_at DESC`에는
  **복합 인덱스 `(bid, received_at DESC)` 하나**가 맞다.
- 단일 인덱스 2개(bid 따로, received_at 따로)로는 안 됨: 각자 한 컬럼만
  정렬해서 "bid로 묶인 상태의 시간순"이라는 **조합**을 못 만든다. bid로 찾은 뒤
  received_at 정렬을 또 해야 함.
- 복합 인덱스는 "먼저 bid로 묶고, 각 bid 안에서 시간 역순 정렬"된 지도 →
  bid 구역으로 점프 → 이미 정렬돼 있으니 위에서 100개 떼면 끝. **필터+정렬 동시 해결.**
- **컬럼 순서:** WHERE로 좁히는 컬럼(bid) 먼저, ORDER BY 컬럼(received_at) 나중.

### 정렬 방향 (DESC)
- 인덱스 기본은 ASC. 단일 컬럼이면 Postgres가 양방향으로 읽어서 ASC/DESC
  차이 거의 없음.
- **복합 인덱스에서 방향이 섞일 때**(예: `ORDER BY a ASC, b DESC`) DESC가 진짜
  중요. 지금 내 쿼리는 사실 방향 없어도 되지만, ORDER BY 방향과 맞춰두면 안전.

### EXPLAIN ANALYZE 읽는 법 (아래→위 실행)
- **Seq Scan** = 전체 훑기(인덱스 없음). **Index Scan** = 지도로 찾기.
- **Filter + Rows Removed by Filter** = 읽고 버림(낭비). **Index Cond** =
  콕 집어 읽음(버림 0).
- **Sort** = 정렬 수행. 복합 인덱스 있으면 이 줄이 **사라짐**(이미 정렬됨).
- **Buffers read** = 읽은 디스크 블록. 인덱스로 41,346 → 68 (600배↓). 시간보다
  본질적 지표.
- 병렬 워커(Gather Merge/Workers) 동원 = DB가 무거운 작업으로 판단. 인덱스 후
  가벼워지면 사라짐.

### 인덱스 효과 (내 측정)
- 단일 쿼리: **85ms → 1.3ms** (65배). 디스크 읽기 600배↓.
- 부하 40유저 p95: **1700ms → 26ms**.
- **데이터 크기에 둔감:** 인덱스 있는 100만 행이 인덱스 없는 1.3만 행보다 빠름
  (로그 시간). 인덱스 = 성능 + 확장성.

### p99 꼬리(tail)의 정체 ★
- **꼬리(p50과 p99 격차)는 "자원 경합"에서 생긴다.** 한정된 자원(커넥션/CPU/락
  등)을 두고 다투면, 운 나쁘게 줄에 걸린 소수가 p99를 튀게 함.
- 내 경우 꼬리의 근원 = **느린 쿼리 + 제한된 풀**. 인덱스로 쿼리를 빠르게 하니
  커넥션 즉시 반납 → 대기 줄 소멸 → 꼬리 소멸(p99 1900→29ms).
- **"평균 멀쩡한데 p99 튐" = 어딘가 경합 있음** 신호. 그 자원을 찾는 게 최적화.

## 5. 더미 데이터 생성 (COPY)

- **가짜 데이터는 "재려는 것에 영향 주는 것만" 현실적이면 된다.** 쿼리가
  bid 필터 + received_at 정렬이니 그 둘만 현실적으로. 메시지 텍스트는 아무거나
  (faker 불필요).
- **bid 편차:** `random.choice`(균등)는 편차 안 생김. `random.choices(bids,
  weights=w, k=1)[0]`로 가중치. `1/(i+1)`이면 Zipf 롱테일(대형 소수 + 소형 다수).
  주의: `k=1`이라도 리스트 반환 → `[0]`으로 꺼내기.
- **received_at:** `now`로 다 찍으면 정렬 무의미 → 인덱스 실험 망함.
  과거 범위에 **랜덤**으로 흩뿌린다(순차 증가도 금지 — 이미 정렬돼서 왜곡). UTC.
- **COPY FROM STDIN:** STDIN = **서버 입장의 입력**. 파일 안 거치고 클라이언트가
  연결로 데이터 스트리밍. 도커 격리 환경에 적합.
- **`write_row`는 "저장"이 아니라 "통로에 흘려보내기".** 실제 적재는
  `async with cur.copy(...)` 블록 끝날 때 한 번에. 한 행씩 코드처럼 보여도
  SQL 파싱/커밋을 행마다 안 해서 빠름. **배치를 안 짜도 COPY가 내부적으로 뭉쳐 처리.**
  → 반드시 **연결·COPY를 루프 밖에서 한 번** 열고, 루프 안엔 `write_row`만.
  (루프 안에서 열고 닫으면 COPY 이점 소멸)
- 성능: 100만 행 COPY ≈ 11.79초. 건당 INSERT(초당 200건)면 83분 → 수백 배.

### random.choices 내부 (측정으로 역추론)
- `choices(weights=...)`는 **매 호출마다 내부에서 누적합(cumulative)으로 변환**.
  그래서 `weights` 넘기기 = 손으로 `accumulate`를 매번 하기 = 같은 시간(13.5s).
- **누적합을 루프 밖에서 한 번 만들고 `cum_weights`로 재사용**하면 그 계산이
  100만→1회로 줄어 빨라짐(11.8s). 핵심은 "불필요한 반복 계산을 루프 밖으로".
- (공식 문서 확인: "supplying the cumulative weights saves work")

### 삭제
- `DELETE * FROM ...` ✗ (DELETE엔 `*` 없음). `DELETE FROM chats WHERE ...` ○.
- 대량 전체 삭제는 `TRUNCATE chats`가 훨씬 빠름(행 하나씩 안 지움). 단 조건(WHERE)
  불가 = 테이블 통째. TRUNCATE는 데이터만 비우고 **인덱스 구조는 유지**.

## 6. 트레이드오프 — 쓰기 vs 읽기 (두 마리 토끼)

- 인덱스는 읽기를 빠르게 하지만 쓰기를 느리게 함(쓰기마다 인덱스 갱신).
  느려짐은 **인덱스 개수에 비례**.
- 내 서비스는 읽기(실시간 중계)가 메인 + 쓰기는 Redis 큐가 완충 → 인덱스로 읽기
  최적화가 맞는 선택.
- 둘 다 중요하면: ① 꼭 필요한 인덱스만 최소로 ② 읽기/쓰기 DB 분리(read replica)
  ③ 배치 쓰기 ④ 큐로 쓰기 부하 흡수. **하나의 DB에서 다 잡기보다 시스템 구조로
  부담을 분산.** 내 시스템은 이미 큐+배치로 ③④를 함.
