# 공부노트 — SOOP 채팅 저장 설계 (1단계)

> 채팅 수집기 → Redis Stream → Postgres 저장 구조를 잡으면서 나온 개념 정리.
> 결정 사항이 아니라 **몰랐던 것 위주**로 남김.

---

## 1. psql — SQL 파일 실행하기

`.sql` 파일은 그냥 텍스트라서 **psql이 먹여줘야** 실행된다. 파일 자체가 실행되는 게 아님.

```bash
# 호스트에 psql이 있을 때
psql -h localhost -p 5432 -U soop -d soop_chat -v ON_ERROR_STOP=1 -1 -f sqls/schemas.sql

# DB만 컨테이너일 때 (파일이 호스트에 있으므로 -f 대신 리다이렉트)
docker compose exec -T db psql -U soop -d soop_chat -v ON_ERROR_STOP=1 -1 < sqls/schemas.sql
```

### 옵션 의미

| short | long | 뜻 |
|---|---|---|
| `-f` | `--file=` | 파일 실행 |
| `-v ON_ERROR_STOP=1` | `--set=ON_ERROR_STOP=1` | 에러 나면 즉시 중단 |
| `-1` | `--single-transaction` | 전체를 한 트랜잭션으로 (실패 시 전부 롤백) |
| `-T` | — | `docker exec`에서 TTY 안 붙임 (파이프/리다이렉트 쓸 때 필수) |

**왜 이 두 옵션이 필요한가**: psql은 기본적으로 문장 하나하나를 따로 커밋한다.
그래서 `CREATE TABLE chats`가 실패해도 그 아래 `CREATE TABLE users`는 그냥 실행돼서
**절반만 적용된 상태**가 된다. `-1` + `ON_ERROR_STOP=1`이면 "전부 되거나 전부 안 되거나".

> Postgres는 **DDL도 트랜잭션이 된다** (MySQL과 다른 점). 그래서 이게 잘 먹힌다.

### psql 메타명령

```
\dt          테이블 목록
\dv          뷰 목록
\d chats     chats 구조 상세 (\chats 아님. \d 가 명령, 뒤는 인자)
\conninfo    접속 정보
\q           종료
```

### 호스트에 psql이 있는지 확인

```bash
psql --version    # 또는 which psql
```

psql은 **클라이언트**라서 서버(컨테이너)와 별개다. DB를 컨테이너로만 돌리면 호스트에 없는 게 자연스럽다.

## 2. `GENERATED ALWAYS AS IDENTITY` vs `serial`

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

조각별로:

- `bigint` — 8바이트 정수(약 920경). `int`는 21억이라 채팅 로그엔 부족할 수 있음
- `GENERATED ALWAYS` — 값을 **DB가 항상 생성**. 직접 넣으려 하면 거부됨
  - 반대는 `GENERATED BY DEFAULT` (직접 넣으면 그 값, 안 넣으면 자동)
- `AS IDENTITY` — 자동 증가. 내부적으로 시퀀스 생성
- `PRIMARY KEY` — 유일 + NOT NULL, 인덱스 자동 생성

### serial의 정체

**`serial`은 타입이 아니라 축약 문법이다.** 이렇게 쓰면:

```sql
CREATE TABLE chats (id bigserial PRIMARY KEY);
```

Postgres가 내부적으로 이렇게 푼다:

```sql
CREATE SEQUENCE chats_id_seq;
CREATE TABLE chats (id bigint NOT NULL DEFAULT nextval('chats_id_seq'));
ALTER SEQUENCE chats_id_seq OWNED BY chats.id;
```

즉 실제 컬럼 타입은 그냥 `bigint`고, **기본값이 "시퀀스에서 다음 번호 뽑기"로 설정된 것**뿐.

### 진짜 차이

serial에서 id는 **그냥 기본값**이라 직접 넣으면 들어간다:

```sql
INSERT INTO chats (id, ...) VALUES (999, ...);   -- 통과됨
```

문제는 **시퀀스가 이걸 모른다**는 것. 시퀀스는 여전히 1, 2, 3…을 세다가
나중에 999에 도달하면 PK 충돌로 터진다. **그것도 몇 달 뒤에.**

IDENTITY의 `GENERATED ALWAYS`는 이걸 아예 차단한다.

| | serial | GENERATED ALWAYS AS IDENTITY |
|---|---|---|
| 표준 SQL | ❌ PG 고유 | ✅ SQL:2003 |
| id 직접 입력 | 됨 (사고 위험) | 차단됨 |
| 정체 | 컬럼 기본값 | 컬럼 자체의 속성 |

> `OWNED BY` 덕분에 요즘은 serial도 테이블 삭제 시 시퀀스가 같이 지워진다. 그건 차이 없음.

### 시퀀스 구멍

트랜잭션이 롤백되거나 서버가 죽으면 그 번호는 버려지고 **재사용되지 않는다.**
id가 1, 2, 3, 7, 8처럼 뛸 수 있음 — **정상 동작**.

→ **id 개수로 채팅 수를 세면 안 된다. `COUNT(*)`를 쓸 것.**

### 시퀀스는 테이블마다 독립

컬럼마다 자기 시퀀스가 생긴다 (`<테이블>_<컬럼>_seq`).
chats가 500만까지 가도 users는 1번부터. 서로 모르는 사이.

## 3. `text[]` — 배열 타입

### 표준 SQL 맞다

배열은 SQL:1999에 들어간 **표준**이다. 표준 문법은:

```sql
parts text ARRAY    -- 표준
parts text[]        -- PG의 짧은 표기 (둘 다 됨)
```

낯설었던 이유는 **표준에 있는데 다른 DBMS가 구현을 안 해서**다.
MySQL·SQL Server엔 배열 타입이 아예 없고 Oracle은 VARRAY라는 다른 방식.

> "PG가 표준을 잘 지킨다"는 인식은 맞고, 배열은 오히려 그 증거에 가깝다.

### 이번 설계에서 나온 표준/비표준 구분

| 문법 | 표준 여부 |
|---|---|
| `GENERATED ALWAYS AS IDENTITY` | 표준 (SQL:2003) |
| `GENERATED ALWAYS AS (...) STORED` | 표준 (생성 컬럼) |
| `CREATE VIEW` | 표준 |
| 배열, 1-based 첨자 | 표준 |
| `timestamptz` | `TIMESTAMP WITH TIME ZONE`의 PG 약칭 (개념은 표준) |
| `now()` | PG 고유 (표준은 `CURRENT_TIMESTAMP`) |
| 첨자 범위 초과 시 NULL 반환 | PG 동작 |

### 첨자 문법

```sql
SELECT parts[1] FROM chats;              -- 단일 원소
SELECT parts[1:3] FROM chats;            -- 슬라이스 (부분 배열)
SELECT array_length(parts, 1) FROM chats;
```

**Postgres 배열은 1-based** (파이썬처럼 0부터가 아님).

→ 파이썬에서 헤더 뗀 `parts[1:]`을 저장하면
   SQL의 `parts[1]`이 다시 원본 1번(채팅)이 된다. **인덱스 감각이 그대로 유지됨.**

**범위 초과는 에러가 아니라 NULL 반환.** `parts[99]` 해도 안 터진다.
→ 파트가 짧게 온 채팅이 있어도 조회가 실패하지 않음.

### 길이 제약이 없다

`text[]`는 "15개짜리 배열"로 선언하는 게 아니라 그냥 배열.
SOOP이 파트를 늘려도 스키마를 안 고쳐도 되는 건 장점,
반대로 개수를 DB가 보장해주지 않는다는 건 단점. 필요하면:

```sql
CHECK (array_length(parts, 1) >= 6)
```

### 왜 전부 text인가

실제 데이터가 `'0'`, `'3'`, `'-1'`, `'65568|163840'`, `''` 처럼 전부 문자열로 온다.
억지로 int 캐스팅하면 `'65568|163840'` 같은 게 안 들어가고 빈 문자열도 애매해진다.
**로그성 = 원본 그대로 보존**이 목적. 나중에 의미가 파악되면 `parts[5]::int`로 캐스팅해 쓰면 됨.

## 4. VIEW

### 정체: 이름 붙여 저장해둔 SELECT 문

```sql
CREATE VIEW 이름 AS <SELECT 문>;
```

만들고 나면 그 이름을 **테이블처럼** 쓸 수 있다.

```sql
CREATE VIEW chats_view AS
SELECT id, bid,
       parts[1] AS message,
       parts[2] AS user_id,
       parts[6] AS user_nickname,
       parts, received_at
FROM chats;
```

> `chats_view`라는 이름은 임의로 지은 것. 아무 이름이나 가능.

### 핵심: 데이터는 하나뿐

```
[디스크]  chats 테이블  ← 실제 데이터는 여기만
              ↑
          chats_view   ← 데이터 없음. "이렇게 읽어라"는 정의만 저장
```

`chats`에 새 채팅이 들어오면 뷰에 **즉시** 반영된다. 동기화 필요 없음.
같은 데이터를 다른 모양으로 보는 **창문**.

### `AS`의 두 가지 용도

```sql
CREATE VIEW chats_view AS SELECT ...   -- ① "이 뷰의 정의는 = 이 쿼리"
    parts[1] AS message                -- ② 컬럼 별명
```

### 컬럼 이름은 뷰에만 존재

```sql
SELECT message FROM chats;       -- ERROR: column "message" does not exist
SELECT message FROM chats_view;  -- OK
SELECT parts[1] FROM chats;      -- OK (직접 첨자 접근)
```

### "함수"가 아니라 "붙여넣기"에 가깝다

함수로 생각하면 이런 오해가 생긴다:

```
1. chats 500만 행을 다 읽어서 뷰 결과를 만들고
2. 거기서 bid를 거르고
3. 10개만 남김
```

실제로는 **안쪽 쿼리와 바깥 쿼리가 하나로 합쳐진 뒤** 실행된다:

```sql
-- 내가 치는 것
SELECT message FROM chats_view WHERE bid = 'htvv2i' LIMIT 10;

-- PG가 실제로 실행하는 것
SELECT parts[1] FROM chats WHERE bid = 'htvv2i' LIMIT 10;
```

`WHERE`와 `LIMIT`이 안쪽으로 밀려 들어간다 (**predicate pushdown**).
500만 행을 훑지 않고, 인덱스도 그대로 탄다.

→ **뷰를 쓴다고 느려지지 않는다.** 뷰가 무거울까 봐 직접 `parts[1]` 쓸 이유 없음.

> 예외: 뷰 안에 `GROUP BY`·`DISTINCT`가 들어가면 밀어넣기가 안 되는 경우가 있음.

### INSERT는 원본 테이블에

뷰의 `message`는 계산식이라 값을 써넣을 데가 없다.

```sql
INSERT INTO chats (bid, parts, received_at) VALUES (...);   -- 저장
SELECT user_nickname, message FROM chats_view;              -- 조회
```

### MATERIALIZED VIEW

데이터를 진짜 복사해두는 것. 수동 갱신 필요. (지금은 해당 없음)

## 5. Generated Column — STORED vs VIRTUAL

원래 후보였던 방식:

```sql
message text GENERATED ALWAYS AS (parts[1]) STORED
```

### STORED의 문제 — 중복 저장

`parts` 배열 안에도 있고 별도 컬럼에도 실제로 디스크에 쓴다.
채팅 3개 필드면 행당 50~60바이트 중복. 로그성 테이블에선 무시하기 애매한 양.

### "읽기가 빨라진다"는 착각

행을 조회하는 시점에 이미 `parts`를 포함한 **행 전체가 메모리에 올라와 있다.**
거기서 `parts[1]`을 꺼내는 건 디스크 I/O가 아니라 메모리 오프셋 계산 — 나노초 단위.

반대로 STORED는 행 크기를 실제로 키운다:
- WAL도 그만큼 더 씀
- 8KB 페이지 하나에 들어가는 행 수가 줄어듦
- → 같은 양을 읽을 때 더 많은 페이지를 읽어야 함
- → **읽기가 오히려 조금 느려질 수도 있다**

### VIRTUAL (PG 18+)

```sql
message text GENERATED ALWAYS AS (parts[1]) VIRTUAL
```

저장하지 않고 **읽을 때 계산**. 사실상 뷰와 같은 동작인데
별도 이름 없이 `SELECT message FROM chats`가 된다는 게 차이.

- **PG 18부터 키워드 생략 시 VIRTUAL이 기본값** (예전엔 STORED만 있어서 생략 불가 → 옛날 자료 볼 때 헷갈릴 지점)
- 제약: **인덱스를 못 건다**, PK/파티션 키 불가, 논리 복제에 안 실림
  - → 표현식 인덱스로 우회 가능

### 결론

| | 저장 공간 | 비고 |
|---|---|---|
| STORED | 중복 발생 | 읽기 이득은 거의 없음 |
| VIRTUAL | 없음 | PG 18+, 인덱스 불가 |
| VIEW | 없음 | 버전 무관, 가공 얹기 쉬움 |

→ **뷰 채택.** 나중에 뷰 이름 쓰는 게 번거로우면 VIRTUAL로 바꿀 수 있음.
`ALTER TABLE ... ADD COLUMN ... VIRTUAL`은 메타데이터만 바뀌어서 비용 거의 없음.

## 6. 표현식 인덱스

컬럼을 물리적으로 안 만들어도 인덱싱이 된다:

```sql
CREATE INDEX ON chats ((parts[2]));   -- 괄호 두 겹 주의!
```

이러면 `WHERE parts[2] = 'sb950817'` 쿼리가 인덱스를 탄다.

→ "이름 붙은 컬럼이 있어야 인덱스를 건다"는 게 generated column의 명분이었는데, 이걸로 해결됨.

### 인덱스는 나중에

지금은 실시간 쓰기 위주 → **PK만 두고 write를 가볍게.**
읽기가 필요해지는 시점(API 재전송, 배치 집계)에 추가:

```sql
CREATE INDEX ON chats (bid, received_at DESC);  -- 방송별 시간대 조회
CREATE INDEX ON chats ((parts[2]));             -- 유저별 채팅
```

## 7. FK 없이도 조인은 된다 ★

**FK는 조인의 조건이 아니라 무결성 제약이다.**
"참조된 값이 반드시 존재해야 한다"를 DB가 강제하는 것일 뿐, 조인 기능과 무관.

```sql
SELECT c.parts[1] AS message, u.nickname, u.chat_count
FROM chats c
JOIN users u ON u.user_id = c.parts[2]
WHERE c.bid = 'htvv2i';
```

FK 없어도 그냥 된다. 타입만 비교 가능하면 되고, `ON c.received_at::date = d.day`처럼
계산식으로도 조인 가능.

### ORM 때문에 생긴 오해

SQLAlchemy에서 `relationship()`을 쓰거나 `.join(User)`처럼 ON 절을 생략하려면 FK가 필요하다.
그건 ORM이 **ON 절을 대신 추론해주는 편의 기능**이 FK에 의존하는 것이지, 조인 자체의 제약이 아님.
ORM에서도 조건을 직접 쓰면 아무 컬럼끼리나 조인된다.

### 오히려 FK를 넣으면 안 되는 이유

1. insert마다 users를 조회해 존재 확인 → 쓰기 느려짐
2. **배치가 아직 안 돈 신규 유저의 채팅이 거부당해 유실됨**

→ 로그 테이블에 FK를 안 거는 건 실수가 아니라 **의도된 선택**. 포트폴리오에서도 그렇게 설명 가능.

## 8. 자연키 vs 인공키

- **`users`에 id 없음** — `user_id`가 이미 SOOP이 부여한 유일값(**자연키**).
  별도 숫자 id를 얹으면 식별자가 둘이 되고 인덱스만 두 개가 됨.
  조회도 `WHERE user_id = ...`, upsert도 `ON CONFLICT (user_id)`로 잡음.
- **`chats`에 id 있음** — 자연키가 없다. 같은 사람이 같은 시각에 같은 말을 두 번 할 수 있어서
  뭘 조합해도 유일성이 안 나옴.

SOOP의 중복 접속/게스트 표시 접미사일 가능성.

- 같은 사람이면 → user_id를 그대로 PK로 쓰면 **한 유저가 두 행으로 갈라짐**

- `chats`는 원본 보존이라 안 건드려도 됨. **정규화는 users 배치에서만.**

## 9. 시간 컬럼 — received_at vs inserted_at

```
received_at   수집기가 채팅을 받은 시각   (앱이 넘김)
inserted_at   DB에 적재된 시각            (DEFAULT now())
```

Redis 큐가 중간에 끼면 이 둘이 벌어지고, **차이 = 큐 지연**.
성능 측정 때 "병목이 큐냐 DB냐"를 바로 볼 수 있다.

⚠️ `received_at`에 `DEFAULT now()`를 쓰면 안 된다 — 큐 지연이 섞여버림. 반드시 수집기가 찍어서 넘길 것.

### 정렬은 received_at으로 ★

**id 순서로 정렬하면 안 된다.** Redis 큐가 끼면 적재 순서가 실제 발생 순서와 어긋날 수 있다.
id는 식별용이고 **시간축은 `received_at`**.

## 10. 파티셔닝 (나중에, 지금 알아둘 것만)

지금 규모에선 거기까지 갈 일 없지만, "나중에 바꾸려면 재생성"이라는 것만 기억.

## 11. Redis — List / Pub-Sub / Stream

| | 동작 | 문제 |
|---|---|---|
| **List** (`LPUSH`/`BRPOP`) | 꺼내면 사라짐 | 소비자가 둘이 되면 못 씀 (저장 워커가 꺼내가면 API 몫이 없음) |
| **Pub/Sub** | 구독자 모두에게 뿌림 | **저장이 안 됨.** 구독자가 죽어 있는 동안 온 메시지는 영영 유실 |
| **Stream** (`XADD`/`XREAD`) | 로그처럼 쌓이고 소비자가 각자 위치를 가짐 | — |

**Stream 채택 이유**: 저장 워커와 API가 서로 간섭 없이 같은 스트림을 읽고,
워커가 죽었다 살아나도 끊긴 지점부터 이어서 읽는다. 컨슈머 그룹으로 ack/재처리도 됨.

⚠️ Stream은 자동으로 안 지워진다. `XADD`에 `MAXLEN ~ 10000` 같은 상한 필수.
안 그러면 메모리가 계속 차오름.

### 실시간 재전송 경로는 DB를 거치면 안 된다

```
수집기 → Redis Stream → FastAPI → 시청자     (실시간 재전송)
              ↓
          Postgres                          (보관)
```

DB를 거쳐 재전송하면 insert→select 왕복 지연이 붙고, 새 채팅을 알려면 폴링을 돌려야 한다.
Stream을 쓰는 이유가 이 경로를 DB에서 떼어내는 것.

→ 그래서 **Postgres는 write-heavy**가 맞고, 뷰 선택이 정당화됨.

## 12. psycopg vs asyncpg

둘 다 Postgres **드라이버**. 역할은 같고 구현 철학이 다름.

- **psycopg2** — sync 전용. libpq 래퍼. asyncio와 궁합 안 맞음
- **psycopg3** (패키지명 `psycopg`) — async 정식 지원. psycopg2 문법이 거의 그대로 이어짐
- **asyncpg** — libpq 없이 PG 바이너리 프로토콜을 파이썬으로 재구현. async 전용, DBAPI 미준수

### 문법 차이 (플레이스홀더)

```python
# psycopg
await cur.execute("INSERT INTO chats (bid, parts) VALUES (%s, %s)", (bid, parts))

# asyncpg
await conn.execute("INSERT INTO chats (bid, parts) VALUES ($1, $2)", bid, parts)
```

asyncpg는 PG 네이티브 `$1`을 쓰고 인자를 펼쳐서 넘김. 결과도 dict가 아닌 `Record` 객체.

### psycopg3 선택 이유

- 이미 아는 문법 → 학습 비용 거의 0
- **mypy strict 궁합이 낫다.** asyncpg의 `Record`는 값이 `Any`로 나와서
  매번 `cast`하거나 dataclass로 감싸야 함
- 요즘은 성능 격차가 예전만큼 크지 않음 (psycopg3도 COPY 지원 훌륭)

→ asyncpg는 나중에 "insert 성능 한계가 어디지?" 국면에서 **비교 대상**으로 붙이면 좋은 학습 소재.

---

## 13. ORM을 안 쓰는 이유 (이 프로젝트 한정)

1. **워크로드가 ORM이 약한 지점** — 실시간 대량 insert. ORM은 객체를 하나하나 만들어 넣는 구조라 오버헤드
2. **generated column / 배열 첨자가 ORM으로 표현하면 지저분해짐**
3. **학습 목적이면 raw SQL이 남는 게 많다** — ORM은 SQL을 가려주는 도구. SQL/인덱스/쿼리플랜 감각이 먼저
4. **async 스택 일관성** — SQLAlchemy async도 내부적으로 드라이버를 쓰니 한 겹 더 씌우는 셈

→ FastAPI + 커넥션 풀 + raw SQL 조합은 아주 흔하고 잘 돌아간다.

> 단, **ORM 자체를 배우는 게 목표라면 얘기가 다르다.** 나중에 비교용으로.

## 14. Pydantic 자리 — 지금은 없다

Pydantic의 가치는 "믿을 수 없는 입력을 **경계**에서 검증"하는 것.
지금 경로(수집기 → Redis → 워커 → DB)는 양쪽 다 내 코드고,
`parts`는 위치 기반 리스트를 통째로 보존하는 게 목적이라 검증할 스키마가 없다.
채팅마다 모델을 만들면 초당 수백 번 파싱 오버헤드만 붙음.

타입만 붙이고 싶으면 가볍게:

```python
@dataclass(slots=True)
class ChatMessage:
    bid: str
    received_at: datetime
    parts: list[str]
```

**Pydantic이 제자리를 찾는 건 FastAPI 붙일 때** — 응답 모델 정의하면 직렬화 + OpenAPI 문서 자동 생성.

## 15. Alembic — 도입 시점

**Alembic은 ORM이 아니다.** 마이그레이션 도구고, SQLAlchemy가 만들어서 의존할 뿐.
→ "ORM은 안 쓰고 마이그레이션만 쓴다"는 정상적인 조합.

모델 없이 쓰면 마이그레이션을 손으로 작성:

```python
def upgrade() -> None:
    op.execute("ALTER TABLE chats ADD COLUMN inserted_at timestamptz DEFAULT now()")

def downgrade() -> None:
    op.execute("ALTER TABLE chats DROP COLUMN inserted_at")
```

- **못 얻는 것**: autogenerate (모델이 있어야 함)
- **얻는 것**: 버전 순서 보장, `alembic_version` 테이블에 **"지금 DB가 몇 번까지 적용됐나"가 기록됨** ← 이게 핵심 가치. 지금은 "내가 이 ALTER 쳤던가?"를 기억에 의존

### 지금은 아직 이르다

스키마가 계속 흔들리는 국면에선 "DROP 하고 schema.sql 다시 먹이기"가 압도적으로 빠르다.
**Alembic이 값어치를 하는 시점 = 날리면 안 되는 데이터가 생겼을 때.**
그때 `schema.sql`을 첫 리비전으로 넣고 시작하면 이력이 자연스럽게 이어진다.

### SQL 우선 대안

- **yoyo-migrations** — 파이썬, `.sql` 파일을 그대로 마이그레이션으로 사용
- **dbmate** — Go 바이너리, 순수 SQL, 언어 무관

(Alembic이 자료가 많고 FastAPI 생태계 표준처럼 쓰여서 포트폴리오엔 유리)

## 16. schema.sql 관리

### DROP은 파일에 안 넣는다

데이터가 쌓이기 시작하면 파일에 든 DROP이 사고로 이어진다. 눈으로 확인하고 직접 치는 게 맞음.

### 중복 CREATE 시

```
ERROR:  relation "chats" already exists
```

해당 CREATE만 실행 안 되고 넘어간다. **기존 테이블이 덮어써지거나 데이터가 날아가지 않음** (CREATE는 파괴적 동작이 아님).

### `IF NOT EXISTS`는 오히려 비추

에러 대신 조용히 스킵된다 → 스키마를 고치고 다시 돌렸는데
"이미 있음"으로 넘어가서 **파일은 새 정의인데 DB는 옛날 스키마**인 상태를 눈치 못 챈다.
그냥 에러가 나는 게 판단할 기회를 준다.

### 파일 하나 vs 여러 개

지금처럼 테이블 2개면 한 파일이 낫다 ("스키마 전체가 여기 다 있다"가 한눈에).
쪼갤 시점: 테이블 10개 초과 / seed 데이터 분리 / 마이그레이션 도입.

### 파일 안 순서 (FK가 생기면)

- CREATE는 참조되는 쪽이 먼저
- DROP은 반대로 참조하는 쪽이 먼저

## 17. argparse

`sys.argv` 대신. **표준 라이브러리**라 설치 불필요.

```python
parser = argparse.ArgumentParser()
parser.add_argument("bid", nargs="?", default="htvv2i")   # 위치 인자
parser.add_argument("--raw", action="store_true")         # 옵션 인자
args = parser.parse_args()
```

- **`--` 유무가 위치/옵션의 유일한 구분**
- `--batch-size` → `args.batch_size` (하이픈 → 언더스코어 자동 변환)
- `action="store_true"` — 값 없는 플래그. 붙이면 True
- `type=int` — 자동 형변환 + 실패 시 에러 메시지
- `--help` 자동 생성 (대괄호 `[]`로 감싸진 게 선택, 아닌 게 필수)

### nargs

| nargs | 의미 | 결과 타입 |
|---|---|---|
| 생략 | 정확히 1개 (필수) | 값 하나 |
| `"?"` | 0~1개 | 값 하나 |
| `"*"` | 0개 이상 | 리스트 |
| `"+"` | 1개 이상 | 리스트 |
| `2` 등 숫자 | 정확히 N개 | 리스트 |

**위치 인자는 `required=False`가 안 먹힌다** (옵션 전용 파라미터).
선택적으로 만들려면 `nargs="?"` + `default`.

### 순서 규칙

- **위치 인자끼리의 상대적 순서만** 의미 있음. `--옵션`은 어디에 써도 무관
- 명령줄에서도 순서 자유: `x.py htvv2i --raw` == `x.py --raw htvv2i`
- ⚠️ 함정: 값을 받는 옵션 + `nargs="?"` 위치 인자가 붙으면
  `x.py --out htvv2i` 에서 `htvv2i`가 `--out`에 먹힌다 → `--out=파일명`으로 쓸 것

### 이번에 잡은 버그

1. **`if not arg:`는 항상 False** — `parse_args()`가 반환하는 `Namespace`는 언제나 truthy.
   `--raw`를 안 줘도 `Namespace(raw=False)`라는 객체는 존재함. → `if not args.raw:`
2. **argparse와 `sys.argv` 혼용 충돌** — `parse_args()`는 `sys.argv[1:]` 전체를 파싱.
   bid도 argparse에 등록해야 함
3. **`add_argument`를 함수 안에 두면** 두 번 호출 시 "conflicting option string" 에러.
   파서 설정은 함수 밖에서 끝내고 함수는 값만 받게

## 18. bytes 디코딩

`parts`는 `list[bytes]`. `parts.decode()`는 안 된다 (`decode()`는 bytes의 메서드).

```python
decoded: list[str] = [p.decode("utf-8", errors="replace") for p in parts]
```

⚠️ 채팅은 사용자 입력이라 깨진 바이트가 섞일 수 있고,
그러면 `UnicodeDecodeError`로 **수집 루프 전체가 죽는다.**

- `errors="replace"` — 못 읽는 바이트를 `�`로 바꾸고 진행 (권장)
- `errors="ignore"` — 그냥 버림. **잘못됐다는 흔적조차 안 남아서 비추**

### 어디서 디코딩할까

**수집기에서 이미 `list[str]`로 yield하는 게 깔끔.**
저장 코드가 바이트를 몰라도 되고, mypy strict에서 `AsyncIterator[list[str]]`로 타입이 딱 떨어진다.

psycopg에 `list[bytes]`를 넘기면 `bytea[]`로 보내려 하므로, 어차피 한 번은 변환해야 함.

### 0번 인덱스 빼고 dict로 (디버깅용)

```python
d = {i: v.decode() for i, v in enumerate(parts[1:], start=1)}
```

`start=1` 덕분에 키가 원본 인덱스(1~15) 그대로 유지된다.
`enumerate(parts[1:])`로 하면 키가 0~13으로 밀려서 헷갈림.

## 최종 스키마

```sql
CREATE TABLE chats (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    bid         text NOT NULL,
    parts       text[] NOT NULL,
    received_at timestamptz NOT NULL
);

CREATE VIEW chats_view AS
SELECT
    id,
    bid,
    parts[1] AS message,
    parts[2] AS user_id,
    parts[6] AS user_nickname,
    parts,
    received_at
FROM chats;

CREATE TABLE users (
    user_id       text PRIMARY KEY,
    nickname      text,
    first_seen_at timestamptz,
    last_seen_at  timestamptz,
    chat_count    bigint NOT NULL DEFAULT 0,
    updated_at    timestamptz NOT NULL DEFAULT now()
);
```

### 확인용 쿼리

```sql
INSERT INTO chats (bid, parts, received_at)
VALUES ('htvv2i', ARRAY['안녕','sb950817','0','0','3','봉봉봉봉2'], now());

SELECT id, user_nickname, message FROM chats_view;
```

`ARRAY[...]`가 psql에서 배열 리터럴 쓰는 방법. 파이썬에선 `list[str]`을 그대로 넘기면 psycopg가 변환.
